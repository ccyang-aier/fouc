# ADD：Agent-Driven Development 协作框架

ADD 全称是 **Agent-Driven Development**，意思是“由 AI Agent 执行研发工作的协作框架”。它把需求分析、设计、开发、测试、评审和知识沉淀，整理成一套 AI 能读取、按步骤执行、交付证据的方法。

本文根据用户提供的 ADD 与 FOA 资料整理，合并重复内容，保留框架定义、开发思想、活动、技能、检查点及采用现状。资产数量和 FOA 检查结果沿用原资料，原资料未提供对应的仓库版本与检查日期；本次文档整理未重新检查外部 ADD、FOA 或其业务仓库。

本文介绍的方法与 FOA 示例不自动成为 Fouc 的工程规则。Fouc 的项目契约以 [AGENTS.md](../../AGENTS.md) 为准，设计决策统一维护在 `docs/`，`.spec/tasks/` 用于执行跟踪；文中的 FOA 工作区指多仓研发目录，不引入 Fouc 产品中的新资源实体。

## 一、定位与组成

### 1. 两项职责

在 FOA 工作区里，ADD 同时承担两项职责：

- **通用方法库**：保存可复用的角色、技能、规范和模板，可以用于其他项目。
- **FOA 跨仓协作中心**：集中记录涉及 Dubhe、IRouting、Serving_Orchestrator 等仓库的需求、总体设计、接口契约、任务依赖和交付证据。

ADD 主要由 Markdown、YAML、TOML、Skill 和少量检查脚本组成，实际执行工作依靠 Codex、Claude 等客户端。它通过机器可读的约定组织工作，产物和验证证据保存在仓库中。

### 2. 五类资产

| 组成 | 解决什么问题 | 例子 |
| --- | --- | --- |
| **Role：角色** | 谁负责，职责到哪里结束 | 需求分析师、架构师、开发、测试、Reviewer |
| **Skill：技能** | 一类工作怎样完成并验证 | 需求澄清、边界讨论、任务实施、代码评审 |
| **Rule：规则** | 工作中始终要遵守什么 | 先理解再修改、明确所有权、保留验证证据 |
| **Profile：技术规范包** | 使用某种技术时，额外遵守什么 | Go 服务、React 前端、声明式资源编排 |
| **Project knowledge：项目知识** | 当前项目究竟是什么 | FOA 的需求、设计、ADR、接口契约和任务 |

原资料中的通用资产盘点为 **12 个角色、19 个核心技能、17 份核心规则、3 个可选技术规范包**。这些数量属于资料快照，更新时应以对应版本的资产清单和检查结果为依据。

角色是按需使用的职责模板。主会话担任 **Lead**，负责理解目标、组织任务、检查交付和衔接后续工作。阶段、技能、角色分别回答“现在做什么”“怎么做”“谁负责”，三者不能混为一谈。

## 二、七项开发思想

### 1. 先把业务目标和责任边界讲明白，再选择实现

ADD 把两类澄清分开：

- **需求澄清**回答“用户要什么、什么算成功”。
- **边界讨论**回答“这个特性管什么、谁使用、与谁连接、接口责任归谁”。

需求拆成原始需求、功能需求和用户故事，并写出类似“当发生某事件时，平台应产生某个可观察结果”的验收标准，让设计、开发和测试有共同依据。

### 2. 用仓库里的正式产物承接工作

一轮聊天结束后，结论要进入它所属的位置：需求进入需求文档，设计进入特性的 `design.md`，跨特性的架构决定进入 ADR，实施安排进入任务和计划。

**SSOT（Single Source of Truth，单一权威来源）**意味着同一个决定只有一个权威正文，其他地方引用它，减少多份文档各说各话。设计记录目标与约定，真实代码和验证证据反映当前实现；两者冲突时，要显式处理。

长期保留“系统应该是什么”，阶段性的计划、讨论和执行过程在结论吸收后归档。`design-tdd` 技能借用了 Kubernetes 的“期望状态与执行动作”思路，区分长期有效的设计与阶段性执行安排。

### 3. 人负责方向和取舍，AI 负责产出与验证

AI 可以分析需求、比较方案、写代码、跑检查、做预审；业务目标、架构取舍、风险接受和发布批准，保留给负责人。

**Gate（放行检查点）**记录当前环节交付了什么、谁确认、凭什么继续。团队采用时，下一环节的人要参与关键确认，保证设计交出去后，开发和测试接得住。Gate 的具体检查内容见第六节。

### 4. 完成任务要有证据，并经过独立检查

一个正常开发任务的闭环是：

```text
开发实现、自测
  → Lead 检查真实 diff 和验证结果
  → Reviewer 独立评审
  → 开发修复
  → Reviewer 复审
  → Lead 再确认
```

新行为要求先建立失败测试或可重复的失败证据，再用最小实现使其通过。跨服务、真实 UI、部署环境中的用户旅程，需要另做端到端验证；构建成功只能证明其中一部分。

### 5. 给 AI 精确的任务上下文

ADD 采用三层加载：

1. 根入口提供基本规则。
2. 当前任务加载相关角色、技能和技术规范。
3. 补充本次涉及的需求、设计、代码和验收命令。

委派任务时使用 **Context Pack（任务上下文包）**，说明目标、仓库、分支、允许修改的文件、验证方式和停止条件。它减少 AI 猜测，也让并行工作中的责任和文件所有权可检查。

### 6. 从真实业务和变化点出发，控制抽象规模

先识别业务能力、对象、状态、消费者和责任，再决定服务、接口、数据库或技术组件。

通用部分与项目差异分开。一次性差异优先局部处理；出现第二个真实消费者、且差异能够清楚命名时，再提炼共同契约。仓库组织、协议和微服务数量都由项目事实决定。

### 7. 每次交付都应改善下一次工作的条件

修复或交付完成后，同步设计、索引和状态；可复用的教训进入规则、技能或项目约定。通用改进可以回流 ADD 母本，FOA 专属知识留在项目层。

这样积累下来，AI 下一次接手时能直接读取已有知识，用户也少解释一次背景。

## 三、10 项活动与对应技能

ADD 的主工作流正式划分为 **10 项活动**，也称“10 活动池”。常见路线是：

```text
需求澄清
  → 架构与关键决策
  → 确认特性边界
  → 详细设计
  → 拆任务、安排依赖和测试
  → 实现与局部验证
  → 独立评审、修复、复审
  → 集成与真实端到端验证
  → 整理知识，更新长期资料
```

下面的英文名称是中文活动的对应释义，**Skill ID 保留原资料中的仓库名称**。例如，需求阶段叫 *Requirement Elicitation*，使用 `requirement-grill` 技能，由 `req-analyst` 角色负责。

| 序号 | 中文活动 | 英文名称 | 实际 Skill ID | 具体工作与交付 |
| --- | --- | --- | --- | --- |
| **1** | **业务需求收集与澄清** | Requirement Elicitation | `requirement-grill` | 把原始想法问清楚，明确用户、目标、范围和成功标准。交付结构化需求、用户故事和验收标准。 |
| **2** | **项目架构设计** | Architecture Design | `architecture-design` | 确定模块职责、服务边界、技术选择、部署和交互关系。交付项目架构方案。 |
| **3** | **架构决策记录** | Architecture Decision Recording | `adr-decision` | 说明关键取舍的现状、候选方案、选择理由和影响。交付 ADR（Architecture Decision Record，架构决策记录）。 |
| **4** | **特性边界讨论** | Feature Boundary Clarification / Boundary Grill | `boundary-grill` | 明确本特性管什么、适用于哪些形态、谁使用、与哪些系统连接、责任如何划分。交付 `boundary.md`。 |
| **5** | **特性详细设计** | Detailed Feature Design | `design-tdd` | 细化流程、接口、数据结构、异常处理、安全和可靠性，并划分用户故事。交付 `design.md`、`stories.md`。 |
| **6** | **任务拆解与批次规划** | Task Decomposition & Batch Planning | `task-decompose` → `batch-plan`；配合 `test-design` | 把故事拆成可执行任务，明确文件范围、依赖、验收命令，组织执行批次并规划测试。交付任务清单、批次计划和测试计划。 |
| **7** | **编码实施与局部测试** | Implementation & Local Testing | `task-implementation` | 按任务边界修改代码，建立失败证据、完成实现、执行局部测试和项目检查。交付代码、测试及验证结果。 |
| **8** | **独立评审与修复复审** | Independent Review & Re-review | `code-review` | 检查行为、契约、兼容性、安全和测试覆盖；发现问题后由开发修复，再复审。交付问题清单和评审结论。 |
| **9** | **集成发布与端到端验证** | Integration, Release & E2E Verification | `git-workflow`；部署后使用 `e2e-verification` | 完成分支集成和发布；需要真实环境时，单独执行 E2E 任务，验证用户入口到后端结果的完整链路。交付合入、发布和验证证据。 |
| **10** | **知识整理与沉淀** | Knowledge Curation | `knowledge-curate` | 更新设计与索引、对齐任务状态、归档执行资料，把可复用经验补入规则和技能。交付可供下一轮直接使用的项目知识。 |

这些活动可以按需进入、穿插和返工。预期行为明确的小 Bug 可以从问题处理进入复现和修复；架构稳定的特性可以沿用已有架构；设计中发现边界问题时回到边界讨论；任意活动中发现新的架构取舍，都可以插入 ADR，完成决策后再继续原活动。

## 四、活动分工与术语辨析

### 1. 需求、架构、边界、详细设计和任务规划

| 活动 | 核心问题 |
| --- | --- |
| 需求澄清 | 用户到底要什么，怎样算成功？ |
| 架构设计 | 整个系统怎样分工？ |
| 架构决策 ADR | 关键方案为什么这样选？ |
| 边界讨论 Boundary Grill | 这项特性负责到哪里，与谁交接？ |
| 详细设计 | 边界内的功能具体怎样实现？ |
| 任务规划 | 把设计变成哪些具体工作，按什么顺序执行？ |

**Grill** 在这里指通过追问检查模糊点和遗漏。

`design-tdd` 中的 **TDD** 指特性设计说明书这一设计产物；**Test-Driven Development（测试驱动开发）**在实施技能及 `tdd-go` 中表达，需要按上下文区分。

### 2. 活动 6 内部的三项工作

| 工作 | 英文名称 | Skill ID | 解决的问题 |
| --- | --- | --- | --- |
| 拆解任务 | Task Decomposition | `task-decompose` | 为交付这个故事，需要完成哪些可独立验证的任务？ |
| 组织批次 | Batch Planning | `batch-plan` | 任务如何分批、排序和分配，才能满足依赖、避免文件冲突？ |
| 设计测试 | Test Design | `test-design` | 需要验证哪些风险，分别用单元、集成、契约、性能或 E2E 测试证明？ |

测试规划在设计和任务规划时就开始，局部测试随实现完成。真实环境的 **E2E（End-to-End Verification，端到端验证）**在活动 9 部署完成后通过独立任务执行。

## 五、问题处理入口与辅助工作流

除了新需求主线，ADD 还定义了问题处理入口和辅助工作流：

| 工作流 | 英文名称 | Skill ID | 使用场景 |
| --- | --- | --- | --- |
| 问题单处理 | Issue Handling | `issue-handling` | 测试缺陷、线上故障、告警或漏洞进入后，组织定级、定位、修复、回归、评审和沉淀。 |
| 系统化调试 | Systematic Debugging | `systematic-debugging` | 按“复现 → 假设 → 实验 → 隔离 → 修复 → 验证”定位根因，常用于问题处理流程内部。 |
| 只读调研 | Research | `research` | 在事实不足时调查代码、依赖、历史或外部方案，给其他活动提供证据。 |
| 框架反馈 | Framework Feedback | `framework-feedback` | 记录 ADD 自身的规则缺陷、流程问题和已经落地的改进。 |
| 框架同步 | Framework Synchronization | `framework-sync` | 将母本更新合入项目，或把项目中的通用改进回流母本。 |
| 版本价值传播 | Release Communication | `release-communication` | 根据真实交付整理发布说明、价值故事和演示材料。 |

**Issue Handling 是 ADD 的“第二入口”**：新需求从需求活动进入，已有缺陷从问题处理进入，再复用相应的设计、实施、评审和知识整理活动。

## 六、G0～G5 放行检查点

Gate 是检查点，不是额外的工作阶段。

| 检查点 | 检查什么 |
| --- | --- |
| **G0** | 实施前是否读懂相关材料、确认影响范围。 |
| **G1** | 任务清单、依赖和文件范围是否确认。 |
| **G2** | 任务的详细实施方案是否确认。 |
| **G3** | 实施后的 diff 和验证结果是否符合预期。 |
| **G4-task / G4-batch** | 单任务评审、整个批次评审是否通过。 |
| **G5** | 是否完成集成合入并获得确认。 |

检查点连接交付物、确认人和验证证据；不能仅凭活动名称或“已完成”的口头描述判断是否可以继续。

## 七、目录、母本与客户端适配

以下目录属于原资料描述的 ADD / FOA 组织方式：

| 目录或文件 | 实际作用 |
| --- | --- |
| `.add/canonical/` | 通用方法母本，保存角色、规则、技能和技术规范。 |
| `.add/targets/`、`.add/projections/` | 把通用母本适配成 Claude、Codex 可用的格式与蓝本。 |
| `AGENTS.md`、`.codex/`、`.agents/` | Codex 的运行入口和规则。 |
| `CLAUDE.md`、`.claude/` | Claude 的运行入口和规则。 |
| `.spec/` | FOA 的项目知识和跨仓研发产物。 |
| `add.manifest.yaml`、`add.workspace.yaml` | 项目采用哪些能力，各仓职责、路径、检查命令如何配置。 |

**Canonical** 可以理解为“可复用的标准母版”。同一套方法经过适配后供两个客户端使用；项目已有的规则、设置和本地经验通过合并保留。

母本保存可复用方法，项目层保存本项目事实。客户端入口按需加载这些内容，避免把全部资料一次性塞入每个任务。

## 八、FOA 跨仓协作与文档生产示例

### 1. Volcano 调度适配

Volcano 调度适配涉及 Serving_Orchestrator 的调度字段、CRD 和生成 bundle，也涉及 Dubhe 对这些能力的消费。

ADD 保存统一设计、依赖和契约，实现任务分别归属业务仓，各仓独立验证，最后安排跨仓 E2E。契约明确：

- **Serving_Orchestrator** 生成并拥有 CRD / bundle。
- **Dubhe** 消费这些能力与产物。
- **ADD 协作中心**记录统一设计、任务依赖、接口契约和交付证据。

跨仓协作需要同时说明产物所有者、消费者和验证责任，避免多个仓库各自维护同一份契约正文。

### 2. 文档生产

ADD 也把这套方法用于文档生产，配置了以下产物链：

```text
立意 → 大纲 → 正文 → 评审
```

文档与代码分别使用 `doc`、`code` 两套验收标准。`design-tdd` 在这里仍特指特性详细设计文档，不能仅凭技能名称把它理解为测试驱动开发。

原资料记录，`.spec/` 已有 Volcano、etcd、弹性扩缩容、标准 API 增强等特性资料，说明 ADD 已有实际使用记录。

| 框架机械一致性自检 | 通过，0 问题；角色、技能、规则及投影等静态结构检查通过。 | 静态一致性通过与客户端完整执行闭环分别验证。 |
| 工作区验证 | 失败，共 3 项。 | 缺少配置要求的 `../RAGflow`；另外两项仍要求 Volcano 文档为 `draft`，但文档已进入 `implementable`，检查条件落后于资料状态。 |

原检查只读、未修改文件，也未验证两个客户端的完整运行闭环。本次沉淀仅整理这些资料，不执行上述外部工作区的配置修正。
