# Agent-Native Operating Model：组织机制、度量与落地路线

> 基准日：2026-08-11  
> 本文回答：如何从“员工各自使用 Agent”逐步升级为可持续的团队与企业协作方式，而不陷入大平台建设或 Agent 失控。

## 一、组织目标

目标不是把员工替换为 Agent，也不是追求自动化比例最大化。目标是建立一种新的工作系统：

> 人类负责目标、价值判断、边界和问责；Agent 承担可委托的搜索、生成、分析和执行；确定性系统负责权限、状态、校验和交易；组织以结果、风险和总成本评价整个闭环。

这要求同时改造技术、流程、职责和指标。只采购 Codex、Claude Code 或办公 Agent，属于工具升级；只有当工作对象、责任、证据和结果也被重构，才是 Operating Model 升级。

## 二、职责模型

### 1. 中央 Agent Platform Team

负责公共底座，不负责替业务团队写所有 Agent：

- Work Graph、Agent Registry、Delegation/Policy、Context Broker；
- 公共执行沙箱、观测、评测、成本和审计；
- MCP/Skill 准入、模板、SDK、黄金路径；
- 高风险动作策略与跨域互操作标准；
- 平台 SLO、开发者体验和内部产品运营。

### 2. Domain Agent Owner

每个领域 Agent 必须有业务/技术 owner，对用途、知识、权限、评测、成本和退役负责。不能把“平台团队上线了模型”当成业务责任转移。

### 3. WorkObject Owner

每个 Initiative、ChangeSet、Incident、Case 等必须有最终 owner。Agent 可执行子任务，但不能成为责任真空。Owner 决定验收标准、冲突取舍和高风险动作。

### 4. Assurance 与风险职能

安全、法务、数据、质量和架构不应逐项手工审批所有 Agent 工作，而应：

- 将政策编码为可执行规则和测试；
- 提供领域评测集与风险场景；
- 对异常和高风险工作进行抽样/升级评审；
- 独立监控策略覆盖、误放行和逃逸事件。

### 5. Agent Champions / Workflow Designers

分布在各团队中，负责把真实工作拆成可委托合同、建立反馈数据并推动采用。他们不是“提示词高手”，而是懂业务流程、质量和变更管理的工作设计者。

## 三、六项组织制度

### 1. Agent 注册与供应链制度

所有可共享、可定时、可 API 触发或拥有写权限的 Agent 必须注册。个人本地只读试验可轻量豁免，但一旦触达团队数据或产生外部影响，就进入治理范围。

注册项包括 owner、用途、模型、Skill、MCP、数据源、权限、版本、评测、成本上限和到期日。模型、提示、Skill、工具和知识变更都视为供应链变更；高风险 Agent 需要重新评测。

### 2. 委托与职责分离制度

禁止 Agent 通过共享个人长效 token 冒充员工。使用独立 Agent 身份或带 `on_behalf_of` 的短时委托；批准、执行、验收在高风险流程中应由不同主体承担。外发、生产、资金、合同和人员权益相关动作必须明确人类签字点。

### 3. 工作接受制度

Agent 生成的任务、需求、决策、会议结论和客户承诺默认处于 `proposed`，只有被指定 owner 接受后才进入正式状态。这样可防止“自动记录”被误认为“组织已经承诺”。

### 4. 人类注意力预算制度

建立统一 Review Inbox 和评审容量：

- 任务启动时估算人类评审分钟数，而不只估算 Agent 成本；
- 队列超载时限制新工作或降低并行度；
- 同类低风险检查通过策略和抽样自动化；
- 跟踪等待审批时间、驳回率、返工和评审者负载。

### 5. 记忆与知识保留制度

个人偏好、工作对象事实和组织知识分层保存。任何长期记忆都要有来源、owner、敏感级别、TTL 和删除机制。会议总结、Agent 推断和未接受草稿不得自动进入组织事实层。

### 6. 停止、降级与退出制度

每个生产 Agent 都要有暂停开关、凭证吊销、回退到人工/确定性流程的路径和退役条件。供应商不可用、模型质量下降、成本异常或策略覆盖不足时，系统应能降级，而不是让业务完全停摆。

## 四、度量体系：不要用“写了多少”衡量成功

### 1. 结果层

- 目标达成率、收入/成本/风险/周期的真实变化；
- 客户一次解决率、缺陷逃逸率、发布成功率、决策兑现率；
- Agent 参与工作与对照组/历史基线的差异。

### 2. 流动层

- 从意图到接受、从接受到验证、从验证到结果的周期；
- WIP、等待时间、交接次数、阻塞年龄；
- 一次验收通过率、返工率、废弃工作比例。

### 3. 人类注意力层

- 每个完成工作对象的人类评审分钟；
- Review Queue 深度、SLA、打断次数；
- 因 Agent 输出引起的认知切换与重复确认。

### 4. Agent 质量层

- 任务完成率、约束遵守率、工具调用成功率；
- 人工接管率、误操作率、幻觉/不接地率；
- 版本回归、不同重复运行的一致性、生产异常率。

### 5. 经济层

- 每个被接受交付物和每个已实现 Outcome 的总成本；
- 模型/token、执行环境、SaaS、评测和人工评审成本；
- 自动生成但未被采用的“废弃数字产能”。

### 6. 风险与治理层

- Agent 注册覆盖率、明确 owner 覆盖率、到期凭证数；
- 高风险动作正确审批率、策略阻断与误放行；
- 可回放 trace 覆盖率、评测覆盖率、已知漏洞修复周期；
- 数据越权、提示注入、工具供应链和错误外发事件。

## 五、推荐实施节奏

这不是行业统计，而是一份面向中大型部门的规划基线；应根据现有 IAM、数据目录、流程引擎和工程平台成熟度调整。

| 阶段 | 建议完成窗口 | 主要产物 | 成功条件 |
|---|---:|---|---|
| 0. 基线与护栏 | 0–1 个月 | Agent/工具盘点、风险分级、试点指标、最小政策 | 知道谁在用什么、访问什么、如何停掉 |
| 1. 共享语义 | 1–3 个月 | WorkObject v1、Agent Registry、统一 ID、事件映射 | 两类场景能跨系统追踪状态与证据 |
| 2. 受控委托 | 3–6 个月 | TaskContract、Context Pack、短时委托、执行沙箱 | Agent 可替换，任务可复现，权限可撤销 |
| 3. 质量与协作 | 6–9 个月 | Review Inbox、Eval/Trace、Work Room、容量管理 | 评审负担和返工没有随产出同比增加 |
| 4. 跨域规模化 | 9–15 个月 | 多域 WorkObject、A2A 边界、组合治理、Outcome 反馈 | 多团队共享平台但保留领域自治 |

## 六、首批试点组合

不要只选 Coding，也不要一开始选不可逆、高监管场景。建议同时选择三个形态不同但可共享底座的闭环：

### 试点 A：跨服务产品变更

验证 `Initiative → ChangeSet → RepoChange → PR/Evidence → Release → Outcome`，复用现有 `.spec`，重点看跨仓影响分析、评审队列和发布证据。

### 试点 B：客户/内部服务工单

验证 `Case → 分类 → 调查 → 回复草稿 → 批准 → 解决 → 客户确认`，重点看知识 ACL、对外承诺、人工接管和一次解决率。

### 试点 C：经营分析与决策材料

验证 `Question → Metric definition → Query snapshot → Report artifact → Decision → Follow-up`，重点看数据口径、来源、快照、审阅和决策兑现。

这三个试点共同需要 Work Graph、身份、委托、Context Broker、Evidence 和 Review Inbox，却使用不同执行器，能验证基础设施是否真的具有横向价值。

## 七、前 90 天可执行清单

### 第 1–30 天：看清现状并收紧高风险边界

- 盘点团队正在使用的 Coding/办公 Agent、MCP、插件、模型、数据源和自动触发；
- 标记共享 Agent、长效凭证、外发写操作、生产权限和敏感数据；
- 确定三类试点、基线周期、结果指标和对照方式；
- 定义 WorkObject、TaskContract、Evidence、Decision 的 v0.1 Schema；
- 明确 L0–L5 动作等级、禁止项和紧急停止方式。

### 第 31–60 天：建立最薄的工作与委托层

- 给现有工单、repo、文档、Agent 和用户建立稳定 ID 与关系；
- 建 Agent Registry 和 owner/到期机制；
- 为 Coding、数据和办公各实现一个 Context Pack 适配器；
- 用现有工作流引擎实现任务状态、人工步骤、重试和补偿；
- 把 Agent 输出以 Artifact/Evidence 回写，而不是只保存聊天记录。

### 第 61–90 天：用真实工作验证闭环

- 让三个试点各跑 10–30 个真实工作对象；
- 对比周期、一次通过率、评审分钟、返工、成本和异常；
- 上线 Review Inbox 与风险化通知；
- 建立第一批黄金评测、历史回放和失败案例库；
- 召开基于证据的继续/调整/停止评审，而不是演示会。

## 八、Build / Buy / Integrate 决策

### 建议自建或掌握语义所有权

- WorkObject/Decision/Evidence/Outcome 模型；
- 本企业的 owner、风险、委托和审批策略；
- 权威来源映射、Context Pack 规则和结果指标；
- 跨供应商的 Agent/Capability Registry 抽象。

### 建议优先采购或复用

- 模型与通用 Agent 客户端；
- IAM、Secrets、策略引擎、工作流、事件总线；
- Git/CI/CD、项目管理、文档、CRM、ERP、可观测平台；
- 通用 tracing/eval 存储与沙箱基础设施。

### 建议以适配器方式集成

- OpenAI Workspace Agents、Microsoft Agent 365、Gemini Enterprise、ServiceNow、Atlassian 等生态控制面；
- Codex、Claude Code、OpenCode、Qoder、TRAE 等执行入口；
- MCP/A2A/AG-UI/ACP 等协议。

原则是：**采购运行能力，保留企业工作语义、授权策略、证据和结果数据的可迁移性。**

## 九、决策门槛

在扩大到下一阶段前，至少满足：

1. 90% 以上共享/有写权限 Agent 有 owner、用途和到期日；
2. 高风险动作不存在共享个人长效凭证；
3. 试点工作能从目标追踪到制品、验收和结果；
4. Agent/模型/Skill 版本变化能触发回归评测；
5. 评审分钟、返工率或周期至少有一项出现可重复改善，且风险未恶化；
6. 任一 Agent 可被暂停、凭证可吊销、任务可转人工；
7. 供应商替换不会丢失 WorkObject、Decision 和 Evidence 历史。

## 十、最终判断

你们当前的 ADD 是必要起点，但它主要释放“个体执行产能”。下一阶段真正的竞争力来自把这种产能组织起来：让每项工作有目标、有边界、有 owner、有共享状态、有可复核证据、有风险控制，并最终回到业务结果。

最值得建设的不是统一 Agent 客户端，而是一个薄而强的 Enterprise Agent Work Fabric。它一端允许个人选择最适合自己的 Agent，另一端让整个部门仍然像一个可协调、可学习、可问责的系统那样运作。
