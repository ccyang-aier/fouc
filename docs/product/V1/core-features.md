# Fouc V1 核心特性

本文件描述用户可感知的 V1 场景特性。所有特性均依赖 [P0 基础能力](./p0-foundation-capabilities.md)；只有特性验收标准及其依赖的 P0 退出标准同时通过，特性才能标记为完成。

## 一、V1 产品目标

V1 要验证的核心命题是：

> 一名研发人员能否在不迁移本地代码、不在远端配置模型服务的前提下，让本地 Agent 安全获得测试环境事实，并在一个工作对象内完成“受理—定位—修复—验证—审核—回归交接”的可审计闭环。

### 北极星体验

1. Fouc 自动发现本机已安装的 Codex、Claude Code、OpenCode 等 Agent，展示版本、状态和能力；
2. 用户选择默认 Agent，或由 Fouc 按任务需求匹配可用 Agent；
3. 测试人员创建问题或从现有问题系统导入问题；
4. Fouc 将问题绑定到目标环境、部署版本、相关微服务与本地仓库；
5. 远程连接器采集日志、错误、进程、配置摘要、版本和健康状态，形成带来源的环境快照；
6. 受管 Agent 同时读取源码、问题描述和远程快照，提出根因假设与调查计划；
7. 研发人员批准必要操作，Agent 在隔离工作区完成修复；
8. Fouc 组织验证、审核、交付与测试回归，并保留完整证据。

## 二、核心特性

### 1. 本机 Agent 自动发现与统一纳管

**优先级：P0｜所有 Agent 能力的执行底座**

Fouc 首先必须知道用户机器上有哪些 Agent、它们是否可用、能够做什么，并能用统一方式向它们下发任务与接收结果。V1 将 Codex CLI、Claude Code CLI 和 OpenCode CLI 作为首批受管对象。

核心能力：

- 启动与按需扫描时检查 `PATH`、常见安装位置和用户显式添加的路径；
- 识别 Agent 类型、可执行文件路径、版本、运行状态、登录可用性和配置位置；
- 生成标准化 `CapabilityManifest`，描述流式输出、会话恢复、工具审批、模型选择、结构化事件等能力；
- 区分 `AgentInstallation`、`AgentProfile`、`AgentSession` 与 `AgentRun`，避免把一个二进制文件等同于一个运行任务；
- 通过统一 Agent Driver 执行启动、发送任务、追加指令、取消、恢复、终止和状态查询；
- 为每次运行设置工作目录、上下文、模型/配置、权限模式、环境变量白名单和资源限制；
- 将原生日志与事件转换为 Fouc 统一事件流，同时保留原始输出用于诊断；
- 展示各 Agent 的能力差异，不把不支持的功能伪装成可用；
- 允许用户刷新发现结果、设为默认、启用/停用、打开原生终端或解除纳管；
- 安装、升级、卸载与配置修改必须是用户明确触发的操作，不在后台静默执行。

**优先原因与价值**

Fouc 不自研 Coding Agent，因此受管 Agent 就是全部上层工作流的执行引擎。没有可靠的发现、能力探测、会话控制和状态回传，任务编排只能退化成不透明的 Shell 调用，无法实现暂停恢复、审批、审计或故障处理。

该能力让用户无需在 Fouc 中重复安装已有工具或迁移原有账号配置，也让后续 Work Room、远程诊断和企业流程可以面向稳定协议，而不是分别耦合每个 CLI 的细节。

**前瞻性**

Agent 市场会持续变化。以能力清单和 Driver 契约纳管本地 Agent，使新增 Agent 主要成为适配器工作，同时为未来接入桌面 Agent、远程 Agent、企业托管 Agent 和 A2A 端点保留一致管理模型。

**V1 验收标准**

- 自动发现本机存在的 Codex CLI、Claude Code CLI 和 OpenCode CLI，并准确展示路径、版本与健康状态；
- 三种 Agent 均支持基线操作：创建会话、下发任务、流式查看结果、追加指令、取消与结束；
- 对 Agent 不支持的高级操作明确降级，不因统一抽象丢失关键原生信息；
- Agent 退出、崩溃或输出协议异常时，Fouc 能识别失败并保留诊断信息；
- 不复制 Agent 的长期凭据，不破坏用户已有配置，不在未授权时升级或卸载工具；
- 每次操作都关联到用户、工作对象、工作目录、权限与完整审计记录。

详细设计见 [本地 Agent 发现与纳管](./local-agent-management.md)。

### 2. 统一工作对象与 Work Room

**优先级：P0｜V1 的产品骨架**

Fouc 不以聊天会话作为第一层对象，而是以有生命周期的 `WorkObject` 承载一次真实工作。V1 首先支持 `Issue/Incident`，并为后续的 `Requirement`、`ChangeSet`、`Research` 等类型保留统一扩展方式。

每个 Work Room 至少包含：

- 目标、范围、优先级、负责人、参与者、时限和验收标准；
- 问题单、文档、环境、代码仓、分支、提交和服务之间的引用关系；
- 人与 Agent 的消息、计划、任务运行、等待项和异常；
- 根因假设、决策、补丁、测试报告、审批与回归结论；
- 当前阶段、下一责任人、阻塞原因和完整时间线；
- 面向不同角色的同一事实视图。

V1 的 Issue 状态流建议固定为：

`草稿 → 待测试经理审核 → 待研发定位 → 待研发审核 → 待测试经理复核 → 待测试回归 → 已关闭`

退回、重开和阻塞作为明确事件记录，不通过修改历史状态掩盖过程。

**优先原因与价值**

没有统一工作对象，远程连接、Agent 调用和审批只会成为新的碎片化工具。Work Room 是上下文、流程、权限、证据和协作的共同挂载点，使工作可以暂停、恢复、转交和复盘，也让团队能度量周期、等待和返工。

**前瞻性**

未来 Agent 会越来越多，但组织注意力与可靠交接更加稀缺。以工作对象而非会话为中心，使 Fouc 能自然演进为团队级 Work Graph。

**V1 验收标准**

- 能从零创建或从外部问题单导入一个 Issue；
- 能绑定至少一个环境、多个服务/仓库和多个参与角色；
- 能从 Work Room 恢复完整上下文，不要求用户重新粘贴背景；
- 任一状态变更都能追溯触发者、时间、依据和下一责任人。

### 3. 本地—远程联合诊断工作区

**优先级：P0｜首个差异化场景**

该特性让本地 Fouc 与测试或客户环境建立受控连接。远端不需要安装完整 Coding Agent，不保存模型 API Key，也不需要复制全部微服务源码；本地 Agent 通过最小权限通道读取远程事实并执行经过授权的诊断动作。

V1 支持两类接入方式：

- **无代理连接**：通过 SSH、WinRM、Kubernetes API 或现有可观测平台连接环境；
- **轻量 Fouc Relay**：仅负责身份校验、命令白名单、数据裁剪、脱敏、传输和审计，不包含模型与代码理解能力。

核心能力：

- 环境登记、连通性检查、临时凭据和权限范围展示；
- 将服务实例映射到仓库、分支、Tag、Commit 或构建版本；
- 采集日志、错误栈、进程状态、健康检查、资源指标与配置摘要；
- 将结果固化为带来源、时间、环境和脱敏记录的 `EnvironmentSnapshot`；
- 默认只读，远程写操作、重启和配置修改必须单独批准；
- 大体量数据先在远端过滤，只传输任务所需的最小上下文；
- 支持用户观察、暂停、取消或接管远程操作。

**优先原因与价值**

这是现有 Coding Agent 无法独立解决的关键断点，也是最快证明 Fouc 独特价值的入口。它把“把工具搬到环境”改造成“把受控事实带到工作区”，减少环境准备、凭据漂移、源码复制和版本错位。

**前瞻性**

混合部署、零信任和数据不出域会长期存在。将远程环境抽象为受策略控制的能力端点，使 Fouc 未来可接入测试集群、客户私有环境、云资源和边缘设备。

**V1 验收标准**

- 远端无需配置模型凭据或复制源码即可完成联合诊断；
- 准确展示环境运行版本与本地分析代码版本的一致或偏离状态；
- 所有远程调用都有作用域、执行主体、输入、结果和时间记录；
- 敏感字段可在进入 Agent 上下文前按规则脱敏；
- 连接中断后任务可恢复，不把部分结果误标为完整快照。

### 4. 多仓隔离工作区与受管 Agent 编排

**优先级：P0｜连接现有 Coding Agent 的能力层**

Fouc 使用已经纳管的 Agent 作为执行器，通过 Repo Workspace 管理一个问题涉及的多个微服务仓。Fouc 负责工作区准备、任务派发和约束，Coding Agent 负责代码理解、修改和验证。

核心能力：

- 记录仓库、远端、默认分支、个人 Fork、服务归属和依赖；
- 根据环境版本与问题范围选择正确的仓库、Commit 和分析基线；
- 为任务创建隔离 worktree/分支，避免污染研发人员当前工作区；
- 以 `TaskContract` 传递目标、输入引用、约束、权限和验收标准；
- 以 `ResultEnvelope` 接收结论、变更、验证、风险和证据引用；
- 展示计划、运行状态、文件变更、工具调用和等待审批事项；
- 允许在已纳管 Agent 之间切换执行器或分派子任务，同时保留统一工作记录；
- V1 使用单一协调者与有限并行，不追求多 Agent 自由群聊。

**优先原因与价值**

Agent 纳管解决“谁来执行”，本特性解决“在哪些代码上、以什么边界执行”。稳定的任务与结果契约让一次问题覆盖多个微服务仓，而不依赖手工拼接目录和上下文。

**前瞻性**

模型与 Agent 产品会快速变化。Adapter、TaskContract 和 ResultEnvelope 是抵御供应商变化、接入专业 Agent 与企业自建 Agent 的关键。

**V1 验收标准**

- 能从已纳管 Agent 中选择符合任务能力要求的执行器；
- 一个 Issue 能关联并分析多个本地仓库；
- Agent 修改只发生在任务隔离工作区；
- 任务可暂停、取消、重试或人工接管；
- 用户能在批准前查看计划、权限和预计影响范围。

### 5. 可执行研发流程、验证与交付闭环

**优先级：P1｜把个人效率变成组织能力并完成闭环**

#### 5.1 流程与人类门禁

Fouc 将企业研发规范表达为确定性状态机，将 Agent 能力嵌入合适节点。每个节点明确输入、责任角色、允许动作、完成条件、自动检查、审批规则和超时处理。

V1 首先固化两类模板：

1. **问题处理闭环**：测试提单 → 测试经理审核 → 研发定位与解决 → 审核人审核 → 测试经理复核 → 测试人员回归；
2. **轻量变更闭环**：需求澄清 → 影响分析 → 任务拆解 → 开发 → 验证 → 审核 → 交付。

核心能力：

- 流程模板、角色绑定、状态机与阶段验收清单；
- 自动步骤、Agent 步骤、人工步骤和审批步骤的统一编排；
- 只读动作可自动执行，修改、推送、远程写入和发布分级授权；
- 审核收件箱集中呈现需要人类判断的事项；
- 退回原因转化为新的任务约束；
- 超时、失败、取消和重开具有明确语义。

**优先原因与价值**

只有把测试、经理、审核人与 Agent 放入同一责任链，Fouc 才能从个人调试工具升级为团队系统。规范由静态文档变为实际运行的流程，人类注意力集中于高风险判断。

**前瞻性**

未来的关键不是让 Agent 无限制自治，而是让更多工作可以安全委托。确定性流程和人类门禁能够在提高自治度的同时守住责任与质量边界。

**V1 验收标准**

- 两类模板均可创建实例并完整运行到关闭；
- 每个阶段都有明确的进入条件、完成条件和责任角色；
- 审批人可以查看差异、证据与风险后批准或退回；
- 无法绕过必须的审核和回归节点直接关闭问题；
- 自动流转能够解释触发规则和使用的证据。

#### 5.2 证据驱动的验证、交付与知识回流

Agent 的“已完成”不能直接等于企业工作的“可接受”。Fouc 使用 `Evidence` 将根因、代码变更、测试、环境验证、审批和回归结论连接起来，并把结果交付回现有 Git 与问题系统。

核心能力：

- 根因报告：现象、影响范围、版本关系、证据链、根因、修复策略和剩余风险；
- 变更集视图：跨仓补丁、提交关系、契约变更、依赖顺序和影响范围；
- 分层验证：静态检查、单元测试、集成测试、远程环境验证和人工回归；
- 证据采集：命令、测试结果、日志片段、环境快照、审批和回归记录；
- 交付包：提交信息、目标个人 Fork、合并请求描述、测试证据和回滚提示；
- 经用户确认后推送到个人 Fork，并发起或准备合并请求；
- 关闭后沉淀经过验证的故障模式、诊断步骤、服务关系和验证规则。

**优先原因与价值**

原始痛点不仅是定位困难，也包括现场改动回迁、本地重做提交和问题单无法闭环。证据与交付层消除最后一公里的重复劳动，并让研发、审核和测试基于同一事实包工作。

**前瞻性**

随着 Agent 产出速度提升，评审能力与组织信任会成为新瓶颈。证据优先的结果协议为自动评测、质量门禁、审计和跨 Agent 交接奠定基础。

**V1 验收标准**

- 每个关闭的 Issue 都有根因、变更、验证、审批和回归证据；
- 能阻止测试未运行、环境版本不一致等不完整交付；
- 能生成符合个人 Fork → 版本仓流程的交付包；
- 推送与创建合并请求属于显式授权动作；
- 关闭后的知识条目必须引用已验证事实及其来源。

## 三、优先关系

```text
本机 Agent 自动发现与统一纳管
        │
        ▼
统一工作对象与 Work Room
        │
        ├── 本地—远程联合诊断 ──┐
        │                        ├── 可执行流程、验证与交付闭环
        └── 多仓隔离工作区 ─────┘
```

- 第 1 项提供真实、可控、可观测的本地执行能力，是其余特性的前置条件；
- 第 2 项定义所有模块共享的工作语义；
- 第 3、4 项构成“受管 Agent + 远程事实 + 多仓代码”的差异化能力；
- 第 5 项把个人工具提升为团队系统，并把结果接回现有研发链路。
