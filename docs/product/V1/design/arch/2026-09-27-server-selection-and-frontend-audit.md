# 服务端选型与前端组织结构审视

日期：2026-09-27。依据：[项目结构设计](./fouc-project-structure-design.md)。

本次是架构评估，不是前端重构完成记录。检查范围为实际源码、静态 import/export 关系、模块入口、宿主访问、状态归属和构建配置；没有修改页面、样式、数据或权限行为，也没有进行性能压测。长期判断不以已有代码重写成本作为选型依据。

2026-09-28 复查：知识库采用明确的资源选择和共用工作台；工作空间已由应用级上下文统一持有，服务端知识库是具有 workspaceId 的独立实体，一个空间可包含多个知识库。已删除登录分流与工作空间混用的已解决问题记录；当前约束见主设计文档 §2.1—2.3。下文只保留仍适用的审视结论。

## 1. 从零开始的服务端选择

在目前明确的产品目标下，即使没有任何现有代码，也优先采用 TypeScript 实现 Fouc 的核心业务服务，按模块化单体组织；计算处理采用 Python worker，设备执行采用独立 device 运行时，Tauri 保持系统薄壳。

这个结论是针对已知产品工作负载的工程判断，不是宣称 TypeScript 在所有后端场景中都有绝对优势。没有流量、连接数、计算负载、延迟目标、资源预算和团队技术能力等事实，无法证明某一种语言是所有未来场景的唯一最优解。

Fouc 的核心业务包括账户、组织、资源授权、项目状态与需求迭代、连接器、Agent/Skill 管理、Agent 任务编排及实时协作。主要复杂度是这些对象、操作、状态与授权之间的关系，以及外部模型、工具、数据库和执行器的异步交互。调用 AI 模型不等于在业务服务内执行模型推理。

选择 TypeScript 的产品适配依据：

- Web 与桌面共用 React/TypeScript 前端。操作输入输出、事件、状态枚举、领域 schema 和文档协议具有真实的跨端共享需求；可以复用纯契约与协议，无须复用服务端仓储或授权实现。
- Agent 与工具交互、模型流式响应、实时协作需要异步 I/O 与事件处理。TypeScript 可以实现这些职责；当前没有必须由核心业务进程承担大量 CPU 计算的产品要求。
- 协作编辑与前端编辑器协议关系密切，Yjs/Hocuspocus 等 JavaScript 生态组件能提供直接的协议集成。选择时应评估协议实现及运维，不把库存在本身当成强制语言要求。
- 长期扩展的业务模型需要清晰的公开契约、模块依赖和编译期检查。TypeScript 与前端的共同类型系统有价值，但所有不可信请求仍必须做运行时校验与权威授权。

已有实现、测试和集成是执行这项选择的附加收益，不是结论的必要前提。不能用“重写太麻烦”代替产品适配论证，也不能用“换语言更高级”代替工作负载分析。

| 语言 | 在 Fouc 的合理位置 | 成为核心业务服务首选所需的不同条件 |
| --- | --- | --- |
| TypeScript | 核心业务、操作契约、实时协作和 Agent/工具编排 | 当前已知目标支持这一选择；共享类型价值需由真正的契约边界兑现 |
| Python | 文档处理、模型推理、数据分析与相关计算 worker | 若主要产品复杂度转为 Python 计算生态内的业务，或团队长期以 Python 为主，核心服务选择需要重新评估 |
| Go | 可独立部署的网关、执行器或基础设施能力 | 若核心职责转为大量连接、明确的资源限制或其他经测量的运行要求，应按实际设计和压测比较，而不是从“后端”二字直接推导 |

不预先同时引入三种语言，不为目录整齐拆分微服务。TypeScript 是语言选择；Bun/Node 是运行时选择，应另外验证部署、观测与故障行为，不能把选择 TypeScript 等同于已经证明 Bun 在所有生产场景中最优。

## 2. 契约与独立部署

业务服务独立部署，不随每个桌面客户端分发。客户端调用公开服务契约，设备接口和账户服务接口分别认证。

语言相同不意味着允许前端导入后端内部实现。共享范围限于公开 DTO、事件、纯 schema 和文档协议；服务端授权、数据库、队列及事务实现留在服务端。

当前前端通过 `@fouc/server/knowledge-api` 获取公开 tRPC 路由类型，只有类型依赖，不会打包服务运行时。其代价仍然存在：前端编译要解析服务端路由类型图。这种编译期关联可以用于受控的内部客户端，但不能把它描述为语言无关边界。

对需要第三方、跨语言或独立版本消费者的 API，定义明确的网络契约并生成客户端，例如 HTTP 的 OpenAPI。是否保留内部 tRPC，应按消费者和发布方式决定；不用同语言类型推导来替代运行时校验、协议设计或未来正式发布后的接口版本管理。

## 3. 前端整体判断

现有 `src/` 根目录应保留。顶层 `app / shell / features / components / lib` 方向合理，适合共享 Web/桌面的模块化工作台，不需要改名为 workbench 或提前拆成多个应用。

本次盘点 `src/` 共 411 个文件，其中 TS/TSX 403 个；知识库 254 个文件，包含 67 个测试文件。知识库实现较丰富不等于它应该成为平台层，文件数也不构成拆分独立应用的理由。

已有合理之处：

- `app/page.tsx` 保持薄入口，核心内容由工作台装配。
- features 按产品能力组织，知识库内部又按编辑、协作、评论、文档、数据等真实职责拆分。
- 身份会话由应用根级 provider 持有，并非每个页面各建登录状态。
- 数据客户端、查询、纯状态模型与测试在多个子域中已分离。
- 公共 UI 原语独立，CSS Modules 和功能内 CSS 已被采用；全局 CSS 主要承载主题令牌，不能只因文件较长就判为错误。
- 当前静态 import/export 扫描没有发现 lib/components 反向导入 features，或 features 导入 shell；基础依赖方向总体保持。
- 富编辑器已存在动态加载边界，应保留并扩展合理的功能入口加载边界。

这表示基础骨架可以沿用，不表示所有状态和跨模块职责已经正确。

## 4. 需要修正的实际问题

### 4.1 项目状态归属（已修正）

原证据：`src/shell/workbench-shell.tsx` 曾定义项目收藏存储键、读写函数与事件，同时持有 `managementPanel`。

修正：项目列表、当前项目、收藏和管理面板已归 `src/features/project/project-resources.tsx`；服务端项目实体与用例归 `backend/server/src/modules/projects`。状态按当前工作空间与身份分区，shell 只消费模块接口并组合页面。

约束：shell 保留布局、导航容器和窗口行为；任何后续项目业务状态仍由项目模块持有。新项目不能继承开发样例项目的成员、Agent 或工作对象。

优先级：中。

### 4.2 全局通知受知识库页面生命周期控制

证据：`src/shell/system-bar.tsx` 直接装配知识库内部的 `KnowledgeNotificationBell`。`useKnowledgeNotificationsBridge` 在知识库场景内发布快照，卸载时发布 null；铃铛无快照时显示非活动状态。

问题：全局入口依赖进入特定业务页面才拥有通知状态，无法自然承载项目、任务、社区等来源。

目标：已有通知基础设施与全局收件箱归入通知能力，订阅生命周期由应用身份/资源范围管理；知识库只提供具体通知来源和打开目标。保留领域专用事件处理，不建立无限扩展的万能事件总线。

优先级：高。

### 4.3 宿主适配散落，设备失败存在隐式回退

证据：`lib/backend.ts`、`runtime-client.ts`、`fouc-api-endpoint.ts`、`fouc-service-fetch.ts`、`fouc-service-socket.ts`、窗口工具和身份回调多处检查 Tauri 全局对象，检查条件并不一致。设备端点解析在 Tauri invoke 失败后回退到固定本机端口，并非仅在开发环境启用。

问题：功能代码难以得到一致的设备/窗口能力判断，生产桌面连接失败可能被隐藏成另一个本机请求。浏览器缺少本机设备能力也不应自动推导整个模块不可用。

目标：把宿主检测、窗口桥、设备端点、业务服务传输放入明确 platform 分区；业务模块消费能力接口和具体不可用原因。开发回退显式限定开发环境，真实宿主错误准确传播。不制造覆盖所有平台的庞大通用 SDK。

优先级：高。

### 4.4 模块公开入口与前端依赖规则不完整

证据：knowledge 直接访问 identity 的 `auth-api`、`auth-errors`、`identity-provider`；shell 访问 knowledge 通知子目录、project 模型。现有架构检查验证前后端和 workspace 边界，没有约束这些前端内部导入。

问题：目录已经分模块，但消费者仍依赖模块内部组织，未来内部重构容易影响其他能力。

目标：模块仅为真实消费者提供少量公开入口，如页面入口、可复用组件或状态接口；跨模块消费公开能力，检查底层反向依赖和循环。身份会话可作为平台能力，登录/注册场景继续由 identity feature 负责。不要用导出所有内部文件的巨大 index 代替边界，也不要机械禁止合理的跨模块组合。

优先级：中。

### 4.5 顶层功能入口全部静态导入，导航定义重复

证据：`WorkbenchShell` 静态导入各 canvas；视图枚举来自 `navigation-sidebar.tsx`，允许列表在 `workbench-view.ts`，搜索列表在 `system-bar.tsx`，主区还有一套条件分支。视图导航通过 query 参数与 `replaceState` 实现。

问题：新增模块需同步多处定义；静态入口缺少按模块加载边界。源码证据可以说明耦合和加载方式，不能据此直接报告未经测量的首屏耗时。

目标：使用小型且类型明确的导航定义和模块页面加载映射，重型能力按入口加载；导航类型不由视觉组件提供。工作台采用客户端视图导航本身合理，不必把每个小视图强制迁成 Next 路由；需要直接分享的具体资源应有明确 URL 状态，并保持静态导出与桌面兼容。

优先级：中。

### 4.6 子域数据契约使用不一致

证据：`knowledge/data/trpc-client.ts` 同时提供 typed 与 untyped 客户端，注释仍以页面路由尚未装配为理由；服务端当前已装配 page/comment，而 `pages-api.ts` 和 `comments-api.ts` 仍通过字符串路径调用并解析响应。

问题：已经选择 tRPC 后，部分接口未充分利用输入输出推导，且阶段性注释与当前事实不符。其他 untyped 调用需分别核对路由，不能推断全部调用都能直接替换。

目标：统一已公开路由的调用方式，保留对不可信响应的 schema 校验；确有动态调用要求时明确说明。无论采用推导类型还是生成客户端，都应让契约策略一致。

优先级：中。

## 5. 建议的前端目标结构

```text
src/
├─ app/                     Next 路由、布局、应用级 provider 装配
├─ shell/                   工作台布局、导航容器、跨区域组合点
├─ platform/                将现有平台职责准确归类
│  ├─ host/                 Web/Tauri 检测与能力
│  ├─ transport/            service/device 传输和端点
│  ├─ session/              全局身份会话基础能力
│  └─ context/              已明确语义的跨模块资源上下文
├─ features/                业务模块及其真实子域
│  ├─ identity/             登录、注册、账户交互
│  ├─ knowledge/
│  ├─ project/
│  ├─ connectors/
│  ├─ notifications/        提取已有全局通知职责
│  └─ ...                   已有 home/community/automation/settings/session
├─ components/              真正可复用的 UI 组件与 ui 原语
└─ lib/                     纯工具；不含宿主桥、业务仓储或业务状态
```

这是职责目标，不是立即创建全部目录。按现有实现移动真实职责，单个简单模块不强制建立 ui/model/data 三层。复杂模块内可使用 ui、model、data 或已有清晰子域；保留就近测试和模块样式。

允许方向：应用装配与 shell 消费 feature 公开入口；features 消费 platform、公共 UI、纯工具与共享契约；platform 的基础能力不依赖业务页面；lib 与公共 UI 不反向依赖业务。明确的跨模块组合可接受，但不能产生循环或访问内部仓储状态。

## 6. 实施顺序

1. 细化访客主体、内容保留与具体操作规则，在既有统一空间和独立资源模型上推进各模块实现。
2. 整理宿主与传输边界，准确呈现生产失败与开发回退。
3. 调整全局通知生命周期与模块公开入口；项目状态归属已修正。
4. 完善前端边界检查、导航定义与按模块加载。
5. 清理实际子域契约和较大场景组件；用实际职责、复用和复杂度决定拆分，而不是按行数统一拆文件。

前端重构应保持现有 UI、动画、焦点、滚动、编辑状态、错误反馈和已实现行为；产品规则变化应单独明确验证。当前不因目录审视引入新状态库、微前端、通用插件系统、不同的 UI 技术栈或整套路由替换。
