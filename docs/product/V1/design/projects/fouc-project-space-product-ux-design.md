# Fouc 项目工作台与 ADD 产品设计

> 状态：当前项目工作台的唯一产品与 UX 设计。项目工作台现按用户指定的 Synchro Dashboard 视频实现，当前视觉与交互契约见第十三节。项目目录与资源授权保留原有真实边界；视频样例内容仅支撑本机界面交互，尚未接入 ADD 交付对象。本文前十二节描述交付业务目标与现有领域协议，不能将其视为 Dashboard 已完成的业务集成。
> 关联文档：[产品愿景与定位](../../../vision-and-positioning.md)、[V1 核心特性](../../core-features.md)、[P0 基础能力](../../p0-foundation-capabilities.md)、[项目结构设计](../arch/fouc-project-structure-design.md)、[本机 Agent 设计](../agents/fouc-agent-management-design.md)。

## 一、产品定位与设计决策

Fouc 是人与 Agent 协作的超级工作台，研发交付是 V1 首先做深的场景。项目工作台把用户意图、可执行方案、本机 Agent、团队判断、交付证据和运行反馈连成完整闭环；后续研究、分析和办公场景复用目标、执行、证据与决策的基本模型，不把整个产品限制为 Coding Agent。

ADD（Agent 驱动开发）的用户价值在于减少背景重建、人工交接和未经验证的完成判断。人定义预期成果、边界和关键判断；Agent 研究、规划、实现并提交结果；系统通过真实身份、确定性门禁、版本与证据组织协作。Git、工单、文档、CI/CD 与可观测平台继续拥有各自的权威事实。

ADD 交付业务保留以下领域规则；当前 Dashboard 的视觉、样例和接入边界以第十三节为准：

1. 一项交付目标只有一个权威 `WorkObject`，需求、实现、验证、评审、发布与反馈都围绕它发生。
2. 项目默认进入“总览”。有目标时突出当前推进、需要人判断的事项和下一动作；没有目标时直接提供可验收目标的创建入口。
3. 项目保留五个主页面：“总览、交付目标、产物与证据、资源与编排、项目动态”。待我决策、目标话题、成员与权限、项目设置拥有稳定入口。
4. 八个 SDLC 阶段属于具体目标的工作视角。多个目标可以处于不同阶段，项目整体不显示一根虚构的八阶段进度条。
5. 主画布完整承载工作内容。话题、计划、运行与评审可按工作需要展开上下文侧栏；侧栏只显示当前对象的资料或操作，不常驻一个重复项目资料的右栏。
6. Agent 运行结束、生成代码或报告均不等于交付完成。只有当前版本的验收覆盖、测试、安全证据与人工判断满足门禁后，才能推进交付。
7. 本机项目与服务端项目采用同一领域契约，但存储来源和授权边界明确；登录、退出不会迁移、替换或复制当前项目。
8. 所有模块使用真实持久化数据。空数据、加载、读取失败、权限拒绝、设备不可用与外部服务未配置分别呈现，不注入演示任务、成员、Agent、指标或成功记录。

## 二、对象模型与资源边界

| 对象 | 用户心智 | 当前职责 |
| --- | --- | --- |
| `Project` | 一个项目及其协作边界 | 独立目录、名称、来源、成员与项目设置 |
| `WorkObject` | 一项可验收的交付目标 | 需求、缺陷或改进；持有目标、规格、计划、运行、证据、决策与反馈 |
| `WorkRoom` | 目标的完整工作页面 | 同一目标的八个阶段视角，是界面组合，不建立另一份业务对象 |
| `TaskContract` | 一次受控委托 | 由当前目标、规格、计划、执行目录、角色、权限与预算共同形成；当前绑定于目标及运行版本，不另建重复任务库 |
| `AgentRun` | 一次真实执行 | 关联设备会话与运行 ID，记录目录、Git 事实、事件、结果、失败与取消 |
| `Artifact` | 可复核的产物引用 | 规格、方案、代码、测试/安全报告、文档、链接与发布结果 |
| `Evidence` | 支撑验收的事实 | 类型、结果、来源、适用版本、验收条件覆盖及人工核验记录 |
| `Decision` | 人承担责任的判断 | 规格、方案、评审、发布和反馈闭环的批准、退回或拒绝及依据 |
| `Release` | 一次版本固定的发布请求 | 环境、适配器、批准、实际执行状态、远端运行 ID 与结果 |
| `Feedback` | 运行后发现与学习 | 关联发布，可原子创建新的跟进目标并保留来源 |

项目以 `projectId`、知识库以 `knowledgeBaseId` 独立管理，不设全局工作空间或默认空间。知识库拥有文件夹和文档；项目只显式引用经授权的内容。项目成员资格不授予任何知识库读取权限，文档引用也不改变文档归属。

当前 `WorkObject` 支持 `requirement`、`bug`、`change` 三种类型和标准、快速缺陷两种模板。快速模板用于缩减小范围修复的文档负担，不取消明确验收、人工确认、验证与发布门禁。研究和办公模板属于后续产品化范围，当前不能将它们列为已经可执行的模板。

## 三、ADD 与 SDLC 的完整闭环

工作流按“明确成果 → 受控执行 → 交付与学习”组织。八个阶段提供稳定的阅读和操作入口，实施、验证与评审允许反复迭代；反馈产生的新目标继续下一轮。页面选择不是业务批准，用户能查看各阶段内容，但实际执行仍受当前门禁约束。

| 阶段 | 核心问题 | 主要输入与产出 | 人与系统的控制点 |
| --- | --- | --- | --- |
| 目标与验收 | 要改善什么，怎样判断成功？ | 意图、预期成果、约束、验收条件、优先级与负责人 | 至少有明确意图和一条验收条件；来源与责任人真实 |
| 规格与方案 | 用户需要什么行为和解决方案？ | 可编辑需求规格；规划 Agent 可提出研究与规格草案 | 人保存并确认当前范围，Agent 提案不自动成为批准 |
| 架构与编排 | 在哪些边界内，由谁完成？ | 架构选择、风险、角色、依赖、步骤及执行契约 | 确认规格、方案与计划；校验步骤依赖无环和实际引用 |
| Agent 实现 | 如何产生可审查的变更？ | 实际 Agent、模型、目录、预算、任务；运行结果和 Git Diff | 先批准契约；按真实设备能力限制读写、取消和工具许可 |
| 测试与安全 | 当前版本是否满足目标且风险可控？ | 验收覆盖、测试和安全报告；通过、失败或结论不明的证据 | 人核验证据；当前版本的全部验收覆盖、测试与安全均需通过 |
| 人工评审 | 这些变更和证据是否可接受？ | 当前规格、计划、代码与核验证据，评审意见 | 有权限的人批准或要求修改，Agent 评审只是依据 |
| 发布 | 哪个版本可以进入哪个环境？ | 版本固定的申请、批准、人工发布记录或 GitHub Actions 运行 | 项目管理员批准；实际远端版本和运行结果核验后报告状态 |
| 运行与反馈 | 是否实现价值，还有哪些差距？ | 真实使用反馈、关联发布、跟进目标、结果判断 | 实际发布成功后可确认闭环；未连接生产信号不显示健康指标 |

当前同一目标一次只允许一个未结束的 Agent 运行；不同目标可独立推进。计划记录角色与依赖，当前不把它描述为已具备任意多 Agent 自动并行调度或无限自治能力。

## 四、项目导航与内容编排

```text
全局功能栏（项目、会话、知识库等独立资源入口）
└── 当前项目名称与真实来源（项目选择器，不创建工作空间层）
    ├── 总览              当前推进、需要判断、下一动作
    ├── 交付目标          同一组目标的列表 / 看板、搜索与筛选
    ├── 待我决策          当前有权处理的规格、方案、核验、评审、发布
    ├── 产物与证据        目标、来源与适用版本明确的产物库存
    ├── 项目动态          项目与目标的真实事件
    ├── 话题
    │   ├── 目标话题 A    人、Agent 与系统记录的连续对话流
    │   └── 目标话题 B    保持目标、资料与决策的关联
    └── 底部管理入口
        ├── 资源与编排    执行环境、Agent、验证、发布与知识引用
        ├── 成员与权限    真实人类成员、角色与邀请
        └── 项目设置      项目资料与低频配置
```

所有项目入口使用同一套完整骨架。项目选择器的“所有项目”回到项目目录。项目分区与左侧入口共享同一个受控选择；列表和看板点击目标先打开详情侧弹窗，需要深入处理时进入 WorkRoom。关闭、后退与展开返回均保留分区、布局、筛选、滚动位置和输入。已删除或失去权限的对象显示真实错误和恢复入口。

侧栏的话题是目标讨论的投影，采用 Threadline/Cansaas 的组织方式。当前契约下不新建独立群聊、频道成员关系或脱离目标的第二份聊天历史；话题内容、回复、资料与决定均追溯到对应目标。回复分支、未读与置顶属于待实施的交互目标，必须有相应真实状态后才渲染数值与标记。

### 4.1 有目标的交付总览

首页按注意力组织，避免堆叠指标卡片、空表头和重复资料：

1. 紧凑页面头部：侧栏已呈现项目身份，主区只保留简短面包屑、“总览”和新建目标。
2. “需要你决策”：短列表呈现当前可处理事项；每行有目标、判断类型、依据摘要与进入动作，无事项时用一行真实状态收起。
3. “正在推进”：连续紧凑列表呈现目标、阶段、负责人 / Agent、下一步与更新时间，不为每个目标制作大型卡片。
4. 底部“最近动态”与“项目准备”：前者呈现真实更新，后者仅呈现代码、执行与发布等必要连接状态；反馈跟进通过目标与动态回到主工作面。

目标、状态、负责人和证据是主要信息；运行日志、完整历史、目录配置与执行细节按需展开。不展示未经接入或测量的健康评分、完成预测、成本、生产可用率和示例头像。

### 4.2 无目标的真实启动页

空项目保持同样的导航与项目身份。主区显示“还没有交付目标”、新建动作与必要准备入口；新建动作打开一处完整的目标表单：

- 交付名称与预期成果；
- 验收条件和约束边界；
- 类型、模板、优先级及真实负责人；
- 创建交付目标，以及配置执行环境的次要入口。

不添加循环插画、教程大卡或虚构任务。代码、执行与发布的准备状态来自实际读取；未配置不阻止用户保存目标。表单默认值仅为合法类型、流程与优先级，目标正文和验收条件保持空白，不预填演示需求。填入明确目标、预期成果及至少一条非空验收条件后，创建动作才可用。

### 4.3 五个主页面的职责

| 页面 | 内容边界 | 空状态与动作 |
| --- | --- | --- |
| 总览 | 项目内当前推进与注意力，不重复完整库存 | 创建第一个目标；配置环境 |
| 交付目标 | 真实 `WorkObject` 的筛选与布局投影 | 创建目标；筛选无结果时清除筛选 |
| 产物与证据 | 从真实目标加载产物与证据，显示来源与当前/旧版本 | 进入对应目标补充产物或核验证据 |
| 资源与编排 | 当前项目设置、真实 Agent 发现、验证与发布配置、知识引用 | 设置目录与执行器；缺授权时提供真实配置原因 |
| 项目动态 | 已发生的项目、目标、运行报告、决策和团队变更 | 无事件时显示真实空状态；读取失败不显示为零事件 |

项目讨论保留在具体目标中，不另建一份脱离交付的群聊历史。待我决策从当前状态、权限、证据与发布申请派生，不与目标状态分别维护。

## 五、WorkRoom 八阶段界面

WorkRoom 复用项目骨架，使用紧凑目标头部与横向局部页签“目标、规格、计划、执行、验证、评审、发布、反馈”，不再常驻第二条纵向阶段导航。页签分别映射八个 SDLC 阶段：“计划”同时容纳架构与编排，“验证”同时容纳测试与安全。目标标题约 22px，正文基准 14px，正文阅读宽约 680–760px；长文可独占阅读区，执行和评审可按内容分成工作面与上下文操作区。窄屏页签可横向滚动，内容重排而不通过缩小字体增加密度。

- **目标与验收**：编辑意图、约束、验收条件、负责人和优先级；逐条验收条件使用稳定 ID，供证据精确关联。
- **规格与方案**：先阅读当前正文与确认状态，再按需编辑；保存后显示需要人确认的操作带。规划 Agent 输出保留为提案，用户决定采纳内容。
- **架构与编排**：架构正文与计划各有清楚的编辑边界；步骤包含角色、依赖和状态，修改契约后重新确认计划。
- **Agent 实现**：执行契约、任务、模型与运行记录组成一个工作面；明确当前 Agent、目录、角色、预算和读写范围。展示真实状态、结果、Diff、失败、取消及驱动能力。
- **测试与安全**：按验收条件关联证据，分别处理验收、测试和安全类型；失败与结论不明明确显示，未核验证据不会显示为已通过。
- **人工评审**：集中当前版本的规格/方案确认、验收覆盖、测试/安全与运行事实；批准和退回都记录依据与责任人。
- **发布**：申请、批准、执行与结果是不同动作；关联具体版本、环境和外部运行，不能点击后用计时器模拟成功。
- **运行与反馈**：记录实际观察和关联发布；从反馈创建缺陷、改进或需求，原反馈和新目标原子关联；闭环判断保留依据。

快速详情采用约 720–820px 的侧弹窗，容纳概况、计划子任务、讨论与历史，顶部提供展开工作页与关闭。话题资料侧栏约 280–320px；其他配置与管理详情约 400–480px。相邻面板只绘制一条边界。窄屏打开详情时占据可用区，关闭返回原位置并恢复入口焦点。无需上下文时主画布获得完整宽度。

## 六、版本、证据与人工门禁

### 6.1 两种版本职责

`revision` 是并发写入的 CAS 版本。每个修改命令带预期 revision，冲突返回 409，重新加载最新状态并保留用户草稿；它不表示代码质量或交付进度。

`versions = { scope, plan, code }` 固定判断的适用对象：

| 变化 | 版本影响 | 必须重新判断的内容 |
| --- | --- | --- |
| 目标、约束、验收条件或规格实质变化 | `scope` 增加 | 规格、方案、验收证据、评审与发布 |
| 架构、计划定义或执行契约变化 | `plan` 增加 | 方案与计划、验收证据、评审与发布；范围未变时规格确认仍可有效 |
| 建立新的实现运行，或发现已记录代码指纹变化 | `code` 增加 | 当前代码的验收证据、评审与发布 |
| 讨论、反馈、步骤状态或优先级等非定义更新 | revision 更新，适用内容版本不必增加 | 不因无关动态无意义地失效原批准 |

规格批准绑定当前 scope；方案批准绑定当前 scope 与 plan；证据、交付评审和发布绑定完整版本。旧记录保留可追溯历史，但不参与当前版本通过判断。运行记录保存 Git HEAD、工作目录状态及包含未跟踪内容的指纹，不把“运行完成”当作代码已经提交、推送或合并。

### 6.2 当前验收规则

代码版本已建立且没有活动运行后，当前版本中经人核验的证据必须同时满足：

1. 每条验收条件均由最近适用的通过证据覆盖；
2. 最近适用的测试证据通过；
3. 最近适用的安全证据通过。

`failed` 或 `inconclusive` 都不满足通过门禁。记录来源为 human、device 或 ci；设备来源需关联真实完成运行及其版本，CI 来源由真实服务端适配器记录。人工录入的执行描述属于人工证据，不伪装为工具自动验证。人在核验、评审与发布批准时必须具有实际项目权限，Agent 和 CI 不能替人批准。

当前设备报告经前端关联到项目权威状态；服务端身份与设备认证分属不同边界，客户端报告不构成不可伪造的设备证明。发布仍须服务端重新核验批准版本、远端 Git 与实际 CI 运行事实。

## 七、受控 Agent 执行

### 7.1 真实执行协议

先在目标中预留运行，再调用设备项目执行接口，关联真实 `sessionId`、`runId`、目录、分支与代码版本，随后同步事件和结果。缺少真实设备运行 ID 时只能报告预留失败或取消，不能报告执行成功。已加载的未结束运行由项目提供者持续监视，离开执行阶段不停止状态同步；重新进入后读取真实运行状态。

角色分为规划、实现、验证和独立评审。同一个已安装 Agent 可承担多个角色，角色不是虚构团队成员，也不要求默认启动八个进程。模型与驱动能力来自真实安装和探测，版本未知、安装不可用或设备断连分别提示。

执行前校验实际仓库路径和 Git 状态。隔离目录使用受管理的 Git worktree，并保留真实编辑内容；切回已有目录不能隐式清理用户修改。允许写入、运行时间和执行环境不得超出项目授权。运行超时或用户取消结束实际进程树，失败与断连保留真实错误，不自动切换成成功。

### 7.2 Native 与 ACP 能力如实呈现

| 驱动 | 当前执行方式 | 许可与恢复边界 |
| --- | --- | --- |
| Codex Native JSON | 固定只读范围，或经明确授权的独立 worktree 写入；以实际完成/失败事件报告结果 | 不支持执行中提升工具权限；不支持项目运行 resume；超范围应失败并由人调整契约后另开运行 |
| 支持许可事件的 ACP Agent | 使用探测到的只读/计划或监督模式，接收真实工具许可事件 | 只允许真实待处理调用的有效选项；不允许永久放行；项目运行仍不声明已支持 resume |

Windows 的 Bun 宿主使用独立 Node companion 承载 Native CLI 进程及 JSONL 事件，设备运行时负责连接、运行关联、预算与取消；companion 使用受保护的本机通信和固定执行协议，不读取业务数据库。可用性由实际进程和能力检查决定，缺少宿主时显示可恢复错误。

worktree 是代码隔离手段，计划模式是工具策略；当前项目执行能力不宣称已经提供通用 OS sandbox。Native 不具备工具审批时不展示虚假的批准按钮，也不能因用户批准业务方案就绕过固定执行范围。设备子进程过滤 Fouc 数据库、账户、对象存储及发布凭据，保留 Agent 自己必要的模型授权；秘密不进入前端、任务提示或业务运行报告。

当前提供运行、事件、结果、失败与取消；通用暂停/恢复、自动接管、跨设备调度与无人值守长期续跑尚未作为该项目协议实现。

## 八、发布与运行反馈

### 8.1 人工发布

人工发布同样经过当前版本评审、发布申请和管理员批准。开始发布只把请求置为 running；管理员实际完成外部操作后记录成功、失败或取消及依据。回滚是实际回滚后的结果记录，不伪装成已经自动执行了远端回滚命令。本机项目只提供人工发布记录，不借用服务端的 GitHub 凭据。

### 8.2 GitHub Actions 适配器

服务端项目可配置 repository、workflow、ref 和 staging/production 环境。执行前同时满足：

- `FOUC_GITHUB_TOKEN` 为服务端提供真实 Actions 授权；
- 仓库属于 `FOUC_GITHUB_REPOSITORIES` 白名单；
- `FOUC_PROJECT_GITHUB_BINDINGS` 由管理员显式把当前 projectId 绑定到允许仓库；创建项目或拥有项目管理权限不能自行获得其他项目的发布凭据；
- 发布请求属于已评审、已批准的当前 scope/plan/code 版本；
- 实际代码已提交，远端 ref SHA 与验收版本的 commit SHA 完全一致，未提交或未推送的变更不能触发远端发布。

允许的 workflow 需提供 `workflow_dispatch`，声明 `fouc_commit_sha` 和 `fouc_environment` 两个输入。Fouc 发送这两个输入并保存实际返回的运行 ID；dispatch 被接受不是发布成功。轮询重新检查项目仓库授权，并校验 repository、workflow、`head_sha`、运行状态与 `conclusion`。只有对应运行的真实 success 才写入 succeeded；失败、取消或版本不符分别记录，网络错误保持待核验状态。

当前已实现适配器与上述门禁。未配置真实凭据、项目仓库授权或 workflow 时，界面显示具体不可用原因；本机开发验证不能等同于已经完成外部云发布。

### 8.3 反馈形成下一轮目标

反馈可关联具体发布，也可记录独立使用发现。创建跟进时同时写入新目标与原反馈的 followUpId，重复创建被拒绝，避免“已创建”提示与实际目标脱节。反馈、跟进和闭环判断共同保留从意图到实际结果的来源链。

当前支持人工运行反馈和发布结果引用。未连接遥测、日志或监控时显示真实未连接状态，不生成生产健康、漂移告警或学习效果评分。自动生产信号采集、回滚执行和策略自优化属于后续集成范围。

## 九、团队权限、邀请与知识引用

| 主体 | 查看 | 目标编辑与讨论 | 人工核验/评审 | 设置、成员与发布 |
| --- | --- | --- | --- | --- |
| 项目所有者 | 是 | 是 | 经真实人类身份校验 | 可管理；发布需当前版本批准 |
| 项目管理员 | 是 | 是 | 经真实人类身份校验 | 可管理普通成员与项目设置；不能越权管理所有者/管理员 |
| 项目成员 | 是 | 是 | 经真实人类身份校验 | 不能管理项目或执行发布 |
| 项目访客 | 是 | 否 | 否 | 否 |
| Agent / CI | 按其实际执行接口 | 提交报告与结果 | 不能替人批准 | CI 只能报告真实适配器结果 |

服务端依据已验证账户、真实项目成员关系和强制 RLS 授权，每次写入重新检查；最后一位所有者不能被移除或降级。移除成员、降级管理身份时撤销相应未接受邀请。页面隐藏按钮只是反馈，不作为授权依据。

邀请链接绑定指定邮箱、角色、有效期和不可猜测令牌，数据库保存摘要。接受时校验账户邮箱、验证状态、令牌、项目、有效期及邀请发起人的当前管理权限。仅提供链接创建与复制，不假装已发送邮件；被邀请者在加入前也可打开独立接受入口，登录后继续原邀请。

本机项目的 owner 表示当前浏览器资源的本机操作权，不是服务端团队成员资格或远程发布授权。本机可以显式执行人工核验与记录，但不能创建云端成员邀请。

知识引用在选择、保存和实际使用时按目标知识库及页面 ACL 校验。服务端项目不能把本机私有文档写入共享项目。查看者没有目标文档权限时显示“受限文档”，不泄露私有标题或正文；既有受限引用可移除，引用存在不表示可以访问内容。

## 十、存储、并发与交互完整性

- **服务端项目**：项目设置、工作对象聚合、活动和邀请持久化到 `resources.project_delivery_*`；复用真实 `project_member`，以项目事务、CAS 与强制 RLS 保护边界。
- **显式本机项目**：目标、设置和事件在 IndexedDB 内按 projectId 原子保存，复用同一共享状态机；这不是登录失败后的团队副本。浏览器数据清理会影响本机项目，界面来源必须明确。
- **设备运行时**：保存实际 Agent 安装、会话、运行和工作目录事实，不连接账户或共享项目数据库。
- **前端草稿**：按来源、项目、账户与目标隔离。切换阶段、关闭面板、返回列表或更新背景状态时保留输入；成功提交仅清除已提交值，不吞掉提交期间的新输入。

项目切换和身份变化取消旧请求；迟到响应和旧 revision 不覆盖新资源或当前详情。冲突展示最新内容与保留草稿，用户明确复核后再提交。可见页面定期刷新并在回焦时获取团队状态，失去权限清除可见的私有缓存并提供真实错误；当前不将轮询描述为已实现实时协同编辑。

前端交互遵循 [AI 前端开发注意事项](../../../../../AI_FRONTEND_RULES.md)：输入只高亮边框，按钮 loading 使用统一三点动画，反馈由 AppAlert 提供；危险操作使用红色并确认，模态底栏按钮 30px。轻量保存不闪动布局或丢失焦点，键盘阶段导航、关闭回焦、确认取消与双向 Tab 路径完整。视觉材质与共同组件以第十三节的当前有效母版为准，不另外套用独立品牌主题；浅分隔、层次化文字与低饱和状态色负责内容层级。

以下是对一手资料的归纳及 Fouc 的明确设计选择，不把外部产品能力或案例效果当成 Fouc 已实现或已测量的结果。

## 十二、价值指标与实施边界

项目工作台的价值围绕达成结果衡量：目标到可验收交付的周期、人类等待与评审时间、一次验收通过率、返工与重开、边界错误造成的失败，以及反馈到跟进的时间。当前尚未建立足够数据的指标不出现在首页；Agent 运行数、消息数和 Token 消耗不能替代成果价值。

现有协议与部分逻辑包含目标创建、规格与方案确认、真实 Agent 执行、版本化证据核验、人工评审、批准发布与反馈跟进；团队项目另有成员、邀请及资源权限。ADD 交付 UX 与真实端到端验收尚未完成；当前前端工作面按第十三节的视频 Dashboard 实施。外部代码推送/PR 创建、工单双向同步、自动生产监控、通用暂停恢复、跨设备调度、成本预测、任意自动化画布与研究办公模板尚未纳入本次项目协议，不用设计稿宣称已可用。

验收聚焦必要 P0 边界与一次真实流程：保存目标后重载不丢失；Agent 实际运行与取消可查；旧版本批准不能继续生效；未核验或失败证据不能通过；无权限主体和未授权仓库被拒绝；实际发布结果与反馈来源可追溯；页面在空数据、已有目标、编辑、错误与窄屏状态中保持完整操作路径。执行进度与验证摘要统一放在 `.spec/tasks/`，不另建第二份设计或按日期归档方案。

## 十三、当前项目 Dashboard 视觉与交互

### 13.1 参考与落点

用户指定 `opensource/dribbble/produtc-design-01.mp4` 为当前项目工作台的视觉依据。视频为 2880×2160、60fps、1018 帧，应用本体归一后约 1440×1024；灰色展示底板、镜头放大与剪辑不属于应用交互。保留原片英文文案、浅灰导航、白色工作面、黑色主动作、轻描边与低饱和状态色。

从 Fouc 现有项目目录选择项目，进入原有 `?view=projects` 工作台。项目工作面组合自己的导航与顶部工具栏；其他产品视图继续使用原有 Fouc 导航、系统栏与实现。用户通过顶部面包屑或账户菜单返回 Fouc 项目目录。没有选中项目时仍显示真实项目目录，不创建虚构的默认项目或工作空间。

### 13.2 页面构成

- 导航：Dashboard、My Task、Inbox、Reporting、Portfolio、Accounts、Goals，收藏列表与 Help Center。
- 顶部：面包屑、项目搜索、复制链接、通知、更新时间、协作者与 Invite；标题和工具栏固定，主体独立滚动。
- 首屏：四个业务快捷入口、Total Projects / Total Task / In Progress / Completed 指标、四行活动时间轴、团队列表。
- 下方：Today Projects 双列卡片、Upcoming Meeting、Milestone Tracker 双系列柱状图与 Activity。
- 详情：参考中的 Sosro Mobile App 居中模态，负责人、标签、状态、截止日期、优先级及 Description / Comment / Setting；评论正文可独立滚动。

页面、卡片、图表、侧栏、动作表单、任务详情与本机状态分别由项目功能拥有并组合；壳层只选择当前工作面。图表按需加载，字体与视频提取的头像、特色图标在本机提供。样式只作用于项目 Dashboard，不改全局主题或其他模块样式。

### 13.3 状态与交互

工作台内的项目卡、任务、文档、会议、协作者、活动与月度目标拥有各自的数据类型，由同一项目作用域状态管理。这里的项目卡是视频界面的本机组合样例，不是 Fouc 项目目录的新增资源或子项目授权层。新建项目卡不隐式创建任务；任务必须关联一张现存项目卡。My Task 呈现独立任务列表，Portfolio 区分项目卡、文档与收藏，Accounts 呈现已选协作者，Inbox 呈现可读状态的活动，Goals 呈现完成进度与目标。

首页四项统计直接从当前可打开的项目卡和任务计算，不用视频中的 12 / 108 / 12 / 76 作为隐藏基数。卡片进度是关联任务的平均进度，评论与附件数来自实际保存的评论；任务更新、移动或删除会重新计算。为保持可核对的状态，初始样例包含三张项目卡和三个任务，Today Projects 显示视频中的两张重点卡片。

搜索跨项目卡、任务、文档与会议定位具体对象，并支持键盘选择与无结果反馈。收藏直接引用对象的类型与 ID，支持添加、移除和集中管理。打开活动会将其标记已读并进入相应对象，未读数同步侧栏与通知入口；删除对象清理相应收藏投影及活动引用，不保留失效导航。

活动时间轴按任务排期与会议时间生成，支持日期前后移动和 Daily / Weekly / Monthly / Yearly 窗口，重叠事件分泳道呈现。每个条带显示实际进度并打开对应详情。里程碑以持久化的月度目标和已录入历史完成数为依据，将当前已完成任务按截止月份各计一次；重复保存不重复计数，重开、改日期或删除重新计算。鼠标与键盘可查看月份、Target 与 Actual，支持范围切换、目标/历史编辑及 CSV 导出。

详情字段先修改草稿；取消、Esc 与背景点击不提交。Save 保存属性与新评论，弹窗保持打开并将评论区滚到新内容；关闭恢复入口焦点与原滚动位置。`@mention` 提供人员选择与蓝色文字，回复、点赞、评论删除也写入同一草稿。Setting 可编辑任务标题、项目关联、进度、排期与时间轴分类。协作者选择持久化并更新头像与团队列表；它是本机界面成员选择，不授予服务端资源权限。项目卡、任务、会议与文档删除均保留红色强调与确认。

四个快捷入口具有独立表单与数据：发票记录客户、币种、截止日期与明细并计算总额；提案记录客户、范围、预算与有效期；合同记录双方、条款与日期；表单记录问题，提供填写预览、响应保存与响应列表。文档支持草稿、就绪、完成与重开，以及基于实际内容的 HTML / CSV 导出。草稿可保留部分未填写字段，进入就绪或完成前校验完整内容。这些状态是本机记录，不表示已发送发票、签署合同或发布外部表单。

会议拥有标题、日程、时长、议程、参加者、链接和评论，支持创建、编辑、日历 ICS 导出与定位链接。任务、会议和文档链接携带 `source:projectId` 作用域，仅在匹配项目及同一设备已有记录中恢复；不同项目与无作用域的对象链接不会误开同名样例，不假装形成跨设备共享。参考附件的原始文件未随视频提供，点击展示参考说明并可下载说明；新增任务评论可附加不超过 1 MB 的实际本机文件，并在保存后重新下载。

参考中的人物与业务内容仍是该界面的交互样例；不创建真实账户、服务端成员邀请、邮件或外部文档，不调用 Agent 或替代 ADD 的门禁事实。

项目卡、任务、文档、会议、成员、活动和目标在浏览器按 `source:projectId` 独立保存。项目切换以同一键重新挂载工作面，避免将上一项目的状态带入下一项目。本机界面样例与既有项目业务存储分开；登录与退出不迁移、复制或写入服务端数据。尚未发布的旧开发样例直接清理，不维护双轨数据格式。

### 13.4 视觉与验收边界

桌面基准为 280px 导航、68px 顶栏、72px 标题行、24px 页面留白和区域间距；活动卡约 828×384，右栏约 260px，底部两列图表约 548×300。窄屏收敛导航并重排内容，不通过整体缩小画布降低可读性。

复核字体、留白、配色、头像、特色图标与英文文案，并对照首屏、滚动后、月份提示、详情打开及评论保存后的状态。模态底栏遵循 Fouc 的 30px 按钮规范；焦点只强调输入边框，菜单复用共享状态，消息通过 AppAlert。视频没有提供的页面、业务连接与窄屏状态只验证必要交互，不宣称源视频已演示这些能力。
