## 1 客户场景：从运行可视走向日常运维

企业将大模型接入 AI Coding、知识问答等生产业务后，需要持续掌握服务质量、资源状态与承载能力，并及时完成故障处置、容量调整和日常维护。运维人员关心的不只是服务如何运行，还包括当前需要关注什么、可以采取什么操作，以及操作是否达到预期。

FOA 当前已能展示部署、实例、物理节点与加速卡关系，提供时延曲线、加速指标和硬件槽位示意。这些能力承载了第一层的运行可视化，但运维与管理能力仍然薄弱，尚未将“看到了什么”与“接下来应该做什么”连接起来。

![FOA 当前推理服务拓扑](imgs/FOA当前拓扑.jpg)

*图 1：现有拓扑已呈现运行结构，需要进一步连接状态判断、日常操作与效果验证。*

| 当前问题 | 用户遇到的困难 | 本次改造方向 |
| --- | --- | --- |
| 结构与指标可见，缺少关联判断 | 看到异常后，仍需跨页面核对日志、配置与资源 | 围绕同一对象组织状态、指标和诊断依据 |
| 拓扑以查看为主，操作与对象分离 | 找到实例后，仍需另找管理入口、重复确认配置 | 在所选对象上提供与当前状态匹配的操作 |
| 操作粒度与管理需求不匹配 | 只需处理单个实例，却难以确认是否影响整个部署 | 精确呈现操作范围，支持实例级处置与定向变更 |
| 操作结果与服务表现缺少连续反馈 | 实例显示运行后，还需另行确认是否接流、效果是否改善 | 联动展示执行进展、实际接流与服务表现 |

本次改造以**“推理全景透视与交互式便捷运维”**为核心，将全景观测与日常操作融合，让用户在掌握运行状态的同时，便捷完成服务巡检、诊断、管理和调优。

## 2 用户故事：替换异常实例，恢复 AI Coding 业务

企业通过多实例推理服务为 AI Coding 提供模型能力。某个实例异常停止后，可用容量下降，剩余实例负载升高，编码请求出现等待时间增长、生成卡顿。运维人员需要恢复服务能力，同时保持其他健康实例运行。

**发现异常。** 进入服务拓扑，看到首响应时延上升、可用实例减少。展开异常分支，选中已停止的实例，查看所属部署、最近事件、日志，以及关联节点和加速卡，确认需要处理的对象。

**清理实例。** 直接执行“清理异常实例”。系统先保留原实例配置，再展示操作对象与影响范围；确认后只清理目标实例。清理完成，运行拓扑移除该实例，操作记录保留配置和“同配置新建”入口。

**同配置补建。** 系统自动带出原实例的模型、引擎、启动参数和资源规格。用户核对后，从满足资源与部署约束的可用节点中选择新位置，新实例加入原部署，继续使用原服务调用入口。

**跟踪接流。** 新实例出现在拓扑中，连续展示资源准备、模型加载、运行就绪和接流状态。实际请求与输出活动随实例呈现，用户能够确认它已经开始承担服务流量。

**验证恢复。** 对照操作前后的时延、失败情况和吞吐，并通过典型编码请求确认响应与生成恢复正常。整个过程中，其他健康实例未因本次替换被重建、重启或改配。

这条故事贯穿**异常识别 → 目标处置 → 配置复用 → 实例接流 → 效果验证**。用户围绕同一服务连续完成处理，复用已有配置并跟踪恢复效果，减少重复填写与跨页核对。

## 4 Amazing 设计思路：推理全景透视与交互式便捷运维

### 4.1 核心理念与客户价值

**推理全景透视**关联服务表现、运行结构与物理算力；**交互式便捷运维**让用户围绕正在查看的对象，直接完成诊断、配置和管理。两者围绕同一服务和实例联动，使拓扑成为推理服务日常运维与管理的便捷操作控制台。

核心体验是：**运行全貌清晰可见，日常管理触手可及。**

| 核心理念        | 具体设计                                    | 客户价值                         |
| ----------- | --------------------------------------- | ---------------------------- |
| **推理全景透视**  | 贯通服务、部署、实例、节点和加速卡，关联运行状态、请求表现、诊断依据与加速效果 | 从业务表现理解运行全貌，判断异常影响与资源瓶颈      |
| **交互式便捷运维** | 在所选对象旁提供管理操作，复用已有配置，按需选择目标资源，并连续反馈执行结果  | 减少入口查找、参数重填和跨页核对，清楚掌握操作范围与结果 |

FOA 的差异化在于：**软件运行与物理算力贯通、观测与操作联动、变更精确到实例**。从服务表现定位到具体实例与算力资源后，用户可就近完成管理，并在同一页面验证效果。

### 4.2 推理全景透视：贯通运行结构、诊断依据与服务表现

围绕“服务运行在哪里、表现如何、需要关注什么”组织信息，支持从服务整体逐层进入实例和物理资源，再回到服务表现验证判断。

| 透视维度 | 设计要点 | 用户能回答的问题 |
| --- | --- | --- |
| **运行结构** | 呈现服务、部署、实例、节点和卡组关系；多版本保留部署边界，P/D 分离呈现输入处理与输出生成角色 | 服务由哪些实例承载，部署在哪些节点与卡组上？ |
| **状态与影响** | 区分运行、停止、异常与资源健康状态；选中节点或卡组，联动突出关联实例与部署 | 哪些对象需要关注，关联哪些服务，剩余承载能力如何？ |
| **请求与性能** | 关联首响应、输出时延、吞吐、失败、排队和负载；具备数据时进一步展开 P/D 耗时与 KV 传输 | 请求慢在哪个阶段，是容量不足、实例异常还是资源瓶颈？ |
| **诊断依据** | 所选对象的指标、日志、事件和配置使用一致的对象与时间范围，支持同角色实例对比 | 异常发生时有哪些证据，与其他实例有什么差异？ |
| **变更与效果** | 展示操作进展、就绪条件、实际接流及服务趋势，对照操作前后的表现 | 操作执行到哪一步，实例是否真正承担流量，服务是否改善？ |
| **加速效能** | 将 SmartKVCache 命中与 Token 复用、SmartDecoding 草稿接受表现，与时延和吞吐关联 | 加速能力是否生效，对当前服务有什么实际作用？ |

图中区分请求流向与资源承载关系，运行中的实例也可以存在性能异常。诊断结论需要指标、日志与事件支撑；未就绪、无请求、采集缺失和数据过期分别表达，避免仅凭状态颜色判断服务质量。

新实例“运行就绪”“实际接流”和“业务恢复”分别验证。加速累计量与所选时段数据分开呈现，性能收益在可比模型、资源和负载条件下评估，草稿接受量不直接折算为费用或算力节省。

### 4.3 交互式便捷运维：围绕对象完成日常管理

以服务、实例和资源为操作入口，将常用操作放到用户正在观察的对象旁，带入已有配置与筛选条件，并在当前页面持续反馈结果。异常实例替换是其中一个典型场景，同样的交互方式覆盖巡检、扩缩容、配置调整与维护。

| 日常任务          | 拓扑中的操作                           | 便捷设计与结果反馈                      |
| ------------- | -------------------------------- | ------------------------------ |
| **诊断排查**      | 就近查看日志、事件、监控和配置，比较同角色实例，按权限进入容器  | 沿用所选对象和观察时段，关联资源与近期变更，减少重复筛选   |
| **实例管理**      | 按状态提供启动、停止、重建与异常清理               | 说明可执行条件和影响范围；停止运行实例前先处理接流与在途请求 |
| **流量隔离与恢复**   | 暂停向可疑实例分发新请求，保留实例继续排查；修复后恢复接流    | 展示剩余可用容量与在途请求，恢复前检查就绪条件        |
| **复制与容量调整**   | 复制健康或异常实例的配置，新建实例；按部署或 P/D 角色扩缩容 | 自动填充配置、筛选兼容节点；展示调整前后的实例数与资源需求  |
| **配置核对与定向更新** | 对比实例配置，对选定实例执行允许范围内的配置更新         | 展示配置差异、需重启项与实际目标，逐个反馈执行结果      |
| **节点维护**      | 从节点查看承载实例，选择其他节点补建或替换，再处理原节点     | 校验资源与部署约束；运行实例迁换按就绪、接流和退出顺序推进  |

便捷性贯穿四个环节：**操作就近、配置复用、范围明确、反馈连续**。用户始终能确认正在处理谁、需要补充什么，以及下一步如何继续。操作根据状态和权限提供；多选时仅开放适用于全部所选对象的操作，逐项显示成功、失败与可重试状态。

**操作边界：选中对象、确认范围与实际执行目标保持一致。** 实例级清理、更新和替换贯通管理、编排与路由，相关期望状态和接流关系同步调整；处理单个异常实例时，其他健康实例保持原配置并继续运行。

**配置复用：清理前保留原配置，清理后仍可继续新建。** 复用模型、引擎、启动参数和资源规格，目标节点与设备绑定重新确定。候选节点同时满足卡类型、容量、健康、模型访问与部署约束，提交时再次校验。

所有写操作沿用权限、确认与审计，确认内容突出目标、配置变化和影响范围。失败后保留操作记录与配置，用户可以更换节点或重试未完成步骤，已完成的清理或新建不会重复执行。

## 5 UX 设计思路

UX 设计聚焦“推理全景透视与交互式便捷运维”，重点呈现以下内容：

- **服务运行全貌**：贯通服务、部署、实例、节点与加速卡，关联服务表现、异常影响和加速效果，突出软件运行与物理算力的对应关系。
- **日常管理便捷**：围绕用户关注的服务、实例或资源提供相应管理能力，突出配置复用、资源选择与操作范围，减少查找入口、重复填写和跨页核对。
- **操作结果可验证**：关联执行进展、实例就绪、实际接流与服务表现，让用户判断操作是否完成、是否达到预期，并清楚识别受影响对象。

体验上突出从观测、判断到管理和效果验证的连贯性。具体信息架构、交互形式和视觉方案由 UX 团队统筹设计。
