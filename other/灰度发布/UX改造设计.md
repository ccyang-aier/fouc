# 灰度发布 Amazing 界面改造设计

## 1 客户场景：生产服务需要持续升级

模型、推理引擎和部署配置都在迭代。对已经承担生产请求的客户，升级既关系到新能力和性能收益，也关系到正在使用服务的业务。客户需要控制影响范围，在真实请求下观察新版，并保留撤回的选择。

| 典型场景      | 客户要完成的任务                   | 最关心的问题                                      |
| --------- | -------------------------- | ------------------------------------------- |
| 引擎或部署配置升级 | 更换引擎、调整参数或部署方式，改善推理体验与资源效率 | 响应是否更快、输出是否稳定、满载后是否排队，收益是否值得额外资源            |
| 模型版本迭代    | 将新模型、微调权重或新版本逐步投入生产        | 模型输出质量是否更好、接口是否兼容、工具调用和结构化输出是否正常，业务结果是否仍然可用 |
| 指定应用试用    | 先让内部应用或特定业务使用新版            | 哪些应用会进入新版，其他业务是否受影响，目标故障后如何处理               |

FOA 已有多版本部署、权重与 API Key 分流、故障策略和监控基础。当前体验主要按功能组织：版本配置在概览，流量在弹窗中调整，运行表现进入监控查看。用户需要在多个位置查找信息，再自行判断升级是否值得继续。

本次改造聚焦易用性与发布可控性：通过清晰的视图和更少的操作，让用户掌握试用范围、版本表现和发布进展，判断后即可继续放量、完成发布或退出灰度。

## 2 用户故事：为企业 AI Coding 平滑升级主力模型

以企业 AI Coding 升级为例：当前通过 FOA 推理服务调用 DeepSeek-V4.1-Flash，希望切换到能力更强的 DeepSeek-V4.1-Flash-10.17。客户既希望改善代码生成和问题修复效果，也要保证开发人员日常使用不中断，调用地址保持不变。

### 准备：在同一服务下部署新版

运维人员创建新版部署，先不接入生产请求，检查接口兼容性，并使用典型编程任务验证代码生成和工具调用。通过配置对比，确认本次模型变化，以及引擎、参数、资源是否同时发生调整。

### 试用：先让试点团队使用新版

试点团队通过独立 API Key 接入 AI Coding。将这些 Key 分配给新版，其他应用的 Key 继续指向旧版，先在明确的业务范围内试用。提交前看清受影响应用，提交后确认网关已按新方案分流。

客户也可选择按权重分配少量请求。按权重与按 API Key 是两种独立策略，分别适合按请求份额放量、按调用主体试用。

### 判断：新版是否稳定，编程效果是否更好

运维人员选择同一时间段，对照新旧版本的失败率、响应时延和吞吐，结合样本量与负载判断运行表现；业务负责人使用同一批编程任务，对照生成代码、工具调用和测试结果，判断输出是否符合要求。

如果新版响应更快，但生成补丁无法通过原有测试，就继续修复和验证；如果质量符合要求、运行表现稳定，再扩大试用范围。数据不足时继续观察。

### 发布与退出：作出决定后直接执行

验证通过，选择“完成发布”，确认迁移范围后将后续请求切到新版；发现异常，选择“退出灰度”，恢复灰度前的权重或 Key 分配。两种操作均由系统带出方案，用户无需重新填写分流配置。

切换后查看网关生效情况。在途流式请求继续由原版本处理，保留必要的回退时间后，再通过已有版本操作停止不再使用的部署。

## 3 友商实现分析

### 3.1 华为 ModelArts：部署信息分层，版本差异可直接对照

ModelArts 在同一服务下管理多个部署。部署卡片呈现状态和流量比例，选中后查看副本、权重与配置详情；流量调整单独承载，表单同时展示权重和预计比例。调研材料还覆盖按运行副本数自动分配、镜像流量验证，分别服务于流量随容量调整、上线前验证。

TI-ONE 将服务版本、运行状态、副本、资源与流量权重集中在列表中，通过独立弹窗调整权重。实践流程覆盖独立测试、新版零流量部署、小流量验证、逐步放量、异常回切，以及最后的资源清理；观察过程结合版本监控、日志和业务验证。

异常时，用户将权重调回旧版，确认业务恢复后停止新版；全量升级时，将流量切到新版，确认迁移后再缩容旧版。流量切换与资源释放分步执行。

### 3.3 小结

两家均以部署或版本为管理对象，通过多版本并行、权重分流、监控观察和异常回切完成渐进升级。华为提供部署卡片、流量策略和历史版本对照；腾讯以版本列表和独立调流弹窗组织操作，配合监控、日志与业务验证推进发布。

从本次提供的界面与实践流程看，用户仍需在多个位置核对信息、判断效果，再配置下一步分流。FOA 的差异化应集中在这些操作环节，让客户更容易判断，也更容易控制发布过程。

| 友商流程中仍需用户处理的环节 | FOA 的差异化设计 | 对客户的价值 |
| --- | --- | --- |
| 权重主要描述请求份额，具体哪些应用参与试用不直观 | 用已有 API Key 分流明确指定试用应用，展示调用主体与版本的对应关系 | 看清谁在试用、谁继续使用旧版，控制影响范围 |
| 配置对照、监控观察和业务结果验证分布在不同页面或环节 | 在同一版本对比入口查看配置、性能与输出质量，保留版本和筛选条件 | 减少信息核对，更快判断新版是否稳定、是否值得上线 |
| 放量、全量切换和异常回切仍需调整分流配置 | 提供“完成发布”“退出灰度”，预填目标方案或恢复灰度前的分流关系 | 判断后直接操作，减少重复配置和恢复出错 |
| 切流、在途请求处理和资源释放分步执行，需结合多个状态判断进展 | 在版本上下文中展示分流生效、在途请求及资源保留状态，保留已有启停操作 | 看清当前进展，合理安排回退窗口与资源释放 |

## 4 Amazing设计思路：让灰度发布更易用、更可控

### 4.1 客户价值：每个问题都有对应的产品设计

| 客户要回答的问题          | 对客户的价值          | 对应的优势设计                      |
| ----------------- | --------------- | ---------------------------- |
| 先让谁使用新版，其他业务会受影响吗 | 按业务安排试用，控制影响范围  | API Key 指定应用，展示调用主体与版本的对应关系  |
| 新版本稳不稳定           | 及时发现异常，判断能否继续放量 | 新旧版本稳定性趋势对照，结合样本量定位异常时段      |
| 新版本表现怎么样          | 判断响应和吞吐收益是否符合目标 | 自选性能指标和时间范围，对照趋势、差值及资源条件     |
| 输出质量怎么样           | 确认模型输出能够用于实际业务  | 同一任务的新旧输出对照，关联工具调用、测试结果和人工结论 |
| 相比旧版究竟变了什么        | 知道升级内容，理解收益与退化  | 配置差异与性能、质量结果在同一版本上下文中查看      |
| 决定发布或退出后，如何操作     | 减少重复配置，缩短执行时间   | 系统带出目标方案，一次确认完成发布或恢复原分流方案    |

### 4.2 通过 API Key 指定应用试用

FOA 已支持 API Key 定向分流。界面将 Key 名称或备注、脱敏标识与目标版本对应展示，按版本查看试用范围，未分配项单独提示。客户能明确知道哪些调用方会使用新版，以及目标异常会影响谁。

在 AI Coding 场景中，试点团队使用独立 Key 时，可先将其指向新版，其他团队对应的 Key 明确保留在旧版。客户无需修改统一服务入口，就能按团队安排试用、收集反馈，再分批迁移。Key 共用的调用方属于同一分流范围，界面应说明这一关系。

### 4.3 对照运行趋势，判断新版是否稳定

在版本对比中，将两版可用状态、请求失败率、超时等已采集指标放在同一时间范围内查看，保留请求样本量。异常时段可继续进入对应版本的监控或日志，避免仅凭“运行中”状态判断服务正常。

例如，试点团队反馈 AI Coding 偶发无响应，用户可对照同一时段的新旧版本：如果异常集中于新版，就能及时缩小范围、排查或退出灰度；如果请求样本较少，则继续观察，避免过早作出稳定性结论。

### 4.4 自选指标与时间，判断性能收益

性能对比以双版本趋势为主，摘要值、差值和样本量就近呈现。用户可选择首 Token 时延、端到端时延、吞吐等已有指标，以及快捷或自定义时间段；资源规格和负载条件同时可见。

例如，AI Coding 用户既关心首段代码何时出现，也关心整段生成是否更快。客户可选择相关时延指标观察，并结合并发和输出规模判断。如果新版响应更快却占用更多加速卡，也能据此评估收益是否值得投入。

### 4.5 对照同一编程任务，判断输出质量

以相同任务、代码上下文和验证条件，对照两版生成代码或补丁、工具调用及验证结果。支持查看问题样本和人工结论，标明样本集与执行时间；测试结果关联已有验证流程，未执行的验证明确标注。

例如，将同一个缺陷修复任务交给两版模型，检查补丁是否解决问题、是否通过同一组测试，以及修改范围是否符合要求。客户能找到新版改进和退化的具体样例，避免把接口返回成功或生成速度更快直接当作编程效果更好。

### 4.6 将配置变化与新旧表现放在一起看

配置按模型、引擎、参数和资源分组对齐，支持“仅看差异”；同一对比入口切换性能与输出质量，保留所选版本。用户无需重新核对对象，就能查看改了什么、表现如何。

例如，本次计划只将模型升级至 DeepSeek-V4.1-Flash-10.17，配置对比可以帮助确认引擎和资源是否也发生变化。如果新版同时增加了算力，性能提升就需要结合资源变化解释；质量对比则继续确认新模型对编程任务的改善。

### 4.7 一次确认完成发布或退出灰度

在版本区域与对比页就近提供“完成发布”、“退出灰度”。系统预填分流方案，展示目标版本、受影响应用及前后变化，用户一次确认即可执行。

| 操作 | 产品行为 |
| --- | --- |
| 完成发布 | 权重模式预填新版承接全部后续请求的方案；API Key 模式预填该服务现有有效 Key 迁移至新版的方案，提交前逐项展示目标关系 |
| 退出灰度 | 带出进入灰度前保留的权重或 Key 绑定关系，检查恢复目标可用后执行；无法恢复时直接说明原因 |

例如，试点团队确认编程效果达到要求后，可直接完成其他团队的迁移；发现关键工具调用不兼容时，可退出灰度，将本次变更的 Key 恢复到原版本。用户无需回忆原配置、逐个重新绑定。

操作后反馈配置保存和网关生效情况。在途请求与资源保留状态继续可见，版本停止沿用已有操作，便于客户安排回退窗口和资源释放。

## 5 UX 设计思路

UX 设计聚焦“让灰度发布更易用、更可控”，重点呈现以下内容：

- **试用范围清晰**：呈现服务版本、请求流向与试用应用，表达权重分流和 API Key 指定应用的不同含义，让用户理解谁在使用新版、影响哪些业务。
- **版本效果可比**：关联配置差异、稳定性、性能和输出质量，保留必要的时间、样本与资源条件，帮助用户判断新版是否稳定、是否值得上线。
- **发布进退可控**：呈现继续放量、完成发布或退出灰度的目标与影响，以及分流生效、在途请求和资源保留状态，让用户掌握发布进展与回退条件。

体验上突出从范围确认、效果判断到发布决策的连贯性，减少信息核对与重复配置。具体信息架构、交互形式和视觉方案由 UX 团队统筹设计。
